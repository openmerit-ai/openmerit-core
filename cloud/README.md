# OpenMerit cloud

The Node.js app behind `claude mcp add --transport http openmerit https://openmerit.ai/mcp`. It runs as a Rivet Cloud hosted actor node on the Rivet Cloud cluster `openmerit` (slug `openmeritdr2i`, region `us-east4`), served at `https://openmeritdr2i.onrivet.dev`. openmerit.ai's domain router (`demo/domain-router.mjs`) proxies `/mcp`, `/.well-known/oauth-protected-resource` and `/api/*` to it when `CLOUD_APP_ORIGIN` is set.

Not released: nothing here is deployed until the deploy below runs.

## What it serves

| Path | Does |
| --- | --- |
| `POST /mcp` | MCP over streamable HTTP, stateless per request, with the tools `openmerit_recommend`, `openmerit_result`, `openmerit_answer`, `openmerit_tasks` and `openmerit_retire`. Each call needs a Clerk OAuth access token whose audience is `https://openmerit.ai/mcp`; without one it answers 401 with `resource_metadata`, which starts the client's Clerk sign-in. No tool takes an API key |
| `GET /.well-known/oauth-protected-resource` (and `/mcp` after it) | RFC 9728 metadata naming Clerk (`https://clerk.openmerit.ai`) as the authorization server |
| `/api/*` | The account API for app.openmerit.ai, with Clerk session tokens: `me`, `tasks`, `runs`, `endpoints`, `guardrails`, `spend`, `billing/checkout`, `billing/portal`, `account/export`, `account` (DELETE), `disconnect`. The shared contract lists each. Deleting a task (`DELETE /api/tasks/:id`) or the account needs the admin role and a first-factor verification in the last 10 minutes (the Clerk session token's `fva` claim); otherwise the 403 body is Clerk's reverification error, which Clerk's `useReverification` turns into its re-verify prompt and a retry. Deleting a task erases its task and job actors, reports, share links, task-level guardrails and index row, and refuses with 409 while a run is computing. Its runs leave every listing but keep a content-free row, as the spend ledger does, so deleting gives back no evaluations or spend. `GET /api/tasks/deleted` lists who deleted which task and when |
| `POST /api/stripe/webhook` | Stripe only, signature-verified. The source of truth for an account's plan |
| `/api/connections/viktor` | The Viktor connection (see below): `GET` its key's last four characters, credit cap and task table; `POST {apiKey, creditCap}` and `DELETE` (admin), where a 400 for a key without every required scope lists them in `missingScopes`; `PATCH {creditCap}` (admin) changes only the cap, keeping the credits used, results and connection time, which connecting again resets; `POST …/refresh` lists the tasks again; `POST …/tasks/<id>/start` evaluates a waiting task. `POST /api/runs/<job>/approve` (admin) records who approved a connection result's change and when |
| `GET /api/r/<job>.md` | A report as Markdown, for the account's members and for agents with their MCP token. `POST /api/runs/<job>/share` makes a public link |

The account is the token's Clerk organization (`org_id`). Clerk's OAuth access tokens for `/mcp` carry no role, so no MCP tool depends on one, and an MCP call keeps the member's role as the web app's session token last recorded it. A token without one is refused with an error that tells the user to create or choose an organization; the app never guesses an account.

## Actors

- `account` (key: Clerk organization ID), in SQLite: the plan from Stripe, members, endpoints with keys encrypted by `OPENMERIT_KEY_ENCRYPTION_KEY` (AES-256-GCM, the account ID as associated data), guardrails at the environment, agent (`environment:agent`) and task levels, the spend ledger, jobs, tasks and reports. It checks the plan, jobs per hour and concurrent jobs at every job start, and reserves spend against the job's budget, the guardrail caps and the monthly caps before every model call.
- `task` (key: account and task ID): the latest bundle, the labels the user gave, the written cases the user approved, the last result and the watch schedule. Every task is watched: from its first job it checks the catalogue on its schedule and when the catalogue changes, and starts a watch job when the catalogue version is newer than its last run's and the task's state is `watching`. The account computes the state when it is read, from what it stores, so it is never stale:
  - `frozen`: the `watch: false` guardrail, at the environment, agent or task level, keeps a validated model. A lower level can set `watch` either way.
  - `idle`: no `openmerit_recommend` call for the task in `OPENMERIT_IDLE_DAYS` (default 30), so watch runs stop spending OpenMerit's money on unused tasks. `idleSince` says when. Watch runs do not keep a task active; the next recommend call does.
  - `retired`: the coding agent called `openmerit_retire` after removing the model call from the code. It disarms the schedule and keeps the runs and reports; the next recommend call for the task brings it back.
  - Retired is reported before frozen, and frozen before idle. `/api/tasks` returns `state`, `idleSince` and, for older clients, `watching` (`state` is `watching`). Deleting a task is separate from all of these.
- `job` (key: job ID): the workflow Source ▶ Cases ▶ label check ▶ Models ▶ Ranking ▶ Agent eval ▶ Action.
  - **Cases** are the bundle's examples, then up to 12 cases that `openmerit/ranking`'s case writer writes on OpenMerit's OpenRouter key (`OPENMERIT_CASE_WRITER_MODEL`). Writing them is billed to the job. A task's later runs, such as watch jobs, reuse the written cases the user approved and write none.
  - **The label check** waits on the job's queue for `openmerit_answer`. It asks `label_<case>` for each example without an expected answer, and `label_check` (a multi-select) for the written cases: an unticked case is dropped.
  - **Ranking** is `openmerit/engine`'s `evaluateTask`, the policy the CLI runs (see openmerit-core's README, steps 6 and 7), over `openmerit/ranking`'s `createMeasure`. The current model runs every case three times (the `repeats` guardrail), five cases it passed in every run are drawn at random inside a recorded step, the search screens on them, the finalists run every case three times, and challengers are screened before their full runs. Each screen and each repeat is its own measure step with its own ledger keys. The Top 3 are the qualified models, cheapest per call first; the pick is the cheapest of them that costs less per call than the current model, and models within one case per run of the current model's pass count are listed as `nearMisses`. A job that started measuring before this policy was deployed ends `failed` when it next wakes, asking to rerun it, since its recorded steps do not replay under the new one. The pool is the catalogue's models with a capability index (ECI) on OpenRouter, which leaves the others out with a notice, plus the models the customer lists on their own endpoints, which without an ECI are measured as challengers. `progress.planned` estimates the measure steps (the current model's runs, about log₂ of the pool in screens, the finalists' runs, and each challenger's screen and runs) and is exact once the search ends. While a measure step runs, `GET /api/runs/<job>` also returns `live`: the candidate, its passes after each case of that step, the current model's pass rate so far and an estimate of the minutes left at the pace of the steps already done, for the app's live chart; it is null between steps and once the job ends. When the budget refuses a challenger, or a challenger fails, the remaining challengers are left out with a notice and the job finishes on the finalists. A budget refusal before the finalists are measured stops the job with a `stopped` report of what was measured. Text answers are graded by a fixed judge (`OPENMERIT_JUDGE_MODEL`), whose calls count in the job's spend but not in a candidate's cost per call. Each model call's ledger key is the job, the step, the candidate and the case, so a step that Rivet replays after a crash counts no spend twice.
  - **Agent eval** is the engine's `checkAgent` rule; **Action** writes the edit and the report. The pool rule, the provisional pick, the result (Top 3, near misses, pick) and the edit are `openmerit/engine`'s (`eligible`, `provisionalPick`, `taskResult`, `proposeEdit`), which the CLI uses too. The edit replaces only the model ID string literal in each code ref's `spelling`, keeping its quotes, a `provider:` prefix and the code around it, such as an environment variable it falls back from. On OpenRouter it writes the full catalogue ID, and on a customer's endpoint the name that endpoint uses. A ref with no model literal, or a literal that names another model than the current one (a fallback), gets an instruction instead of or beside the edit. The edit comes from the agent bundle connection's Change port (openmerit-core's `src/connectors/agent-bundle.ts`). The result also has `basedOn`, the evidence each decision used by the engine's quality rule (for example "Grader: the expected labels of your examples, from agent-bundle"), and `approval`, the question to ask the user before applying the edit, worded as the CLI's Configure question; the report shows `basedOn` under "Based on". `GET /api/runs/<job>` returns the report with the same `reason`, `cheaperThanCurrent`, `nearMisses`, `basedOn` and `approval` as `openmerit_result`. A result's `fixes` say what resolves some of its `notices`, each naming its notice by its text: `raise_budget` (the job's own budget refused a call; it suggests twice the budget, rounded up to whole dollars), `rerun`, `open` (a page at app.openmerit.ai, such as Connections or a task's or agent's guardrails) and `ask_agent` (an instruction only the coding agent can carry out, such as adding labelled examples). `openmerit_result` prints each as a `Fix:` line under its note. `POST /api/runs/<job>/rerun`, and `openmerit_recommend` with `job_id` instead of a bundle, run that job's task again on the bundle the task last ran on, with its environment and agent; `budgetUsd` (MCP: `budget_usd`, at most $1,000) first sets the task's `budgetUsd` guardrail, keeping its other task-level settings. A rerun starts like any run, within the plan and the spend caps.
  - **Across deploys and crashes** the job resumes from its last completed step. A deploy drains the old version's actors: a step it interrupts, such as a measure step waiting on a model, runs again on the new version with the same ledger keys, so its calls are counted once, and a call cut off mid-answer counts at its reservation, since the provider may have billed it. A step that fails for good ends the job `failed`, with the error, a notice and a report of what it measured; a failed job is not charged an evaluation.
- `viktorJob` (key: job ID): one Viktor task's evaluation, the workflow put ▶ thread ▶ testing ▶ credits ▶ grade ▶ evaluate ▶ action. See The Viktor connection.
- `catalogue` (one): openmerit-core's bundled catalogue, refreshed daily when the app has a refresh source.

The app imports `openmerit/engine` (through `src/engine.ts`) and `openmerit/ranking` from openmerit-core's source, which the image copies.

## The Viktor connection

An admin connects a Viktor workspace on app.openmerit.ai's Connections tab with a Viktor API key (paid Viktor plans only; OAuth comes later) and a credit cap (default 2,000 Viktor credits, $2.50 per 1,000, taken from the customer's workspace). On save the app calls Viktor's `GET /api/public/v1/me` and refuses a key that lacks any of `scripts:execute`, `usage:read`, `threads:create`, `threads:read`, `runs:create`, `runs:read`, `messages:create` and `messages:read`, naming the missing ones; a 401 or 403 says API keys need a paid plan. The key is stored like an endpoint's, encrypted with `OPENMERIT_KEY_ENCRYPTION_KEY` (the account and `viktor` as associated data), and only its last four characters are shown.

The connection itself, what a task is, which tasks can be evaluated, the preset ladder, the scripts sent to Viktor, the grading and the proposed change, is openmerit-core's `src/connectors/viktor/`. The app lists the workspace's scheduled tasks with their model and the credits their runs used in the last 30 days, then starts evaluating the ones it can, highest spend first, while the estimated credits fit under the cap and the plan has evaluations left; each counts as one evaluation (`EVALUATIONS_PER_JOB` in `src/actors/account.ts`). The rest wait with a Start button. Viktor's four system tasks (Heartbeat, Memory Dreaming, Skill Refining, Workflow Discovery) script tasks, tasks that run a script of their own before each run (test mode would not capture it), tasks on the workspace's default model or a pinned model such as `gpt-6-luna` (only the presets ultra > smart > balanced > cheap are compared for now) and tasks already on `cheap` are listed as skipped with the reason.

A `viktorJob` writes a batch script to the workspace's sandbox and starts one Viktor API thread that runs it, since Viktor's test mode needs a parent thread. The script creates temporary copies of the task, each personal, paused, set to one preset and titled `OpenMerit: <task title>`, runs the current model and every cheaper preset three times in test mode, which captures Slack posts and other outside actions instead of sending them, and deletes the copies. The job polls the script's progress file, reads each run's credits, then has OpenMerit's judge (`OPENMERIT_JUDGE_MODEL` on OpenRouter, paid by OpenMerit and metered in the job's ledger) write 5 to 10 checks from the task's instructions and a run of the current model, and grade every run on them. `openmerit/engine`'s `evaluateTask` picks from the graded runs as it does for any task. A failed or drained job cancels its thread and deletes any `OpenMerit: ` copy left behind, and Refresh does the same when no job is running. Run again on a Viktor run (`POST /api/runs/<job>/rerun`, admin only; **Start again** in the app) evaluates the task again within the cap. The client sends a script's arguments inside its code, since Viktor refuses an argument over 2,000 characters.

The result proposes a change, such as "Set Ticket triage test to `cheap`", with a link to Viktor's scheduled tasks. **Approve change** records who approved it and when, and the first approval stands; it does not change the Viktor task. `openmerit_tasks` lists the Viktor tasks and their status, and `openmerit_result` shows a Viktor result with its proposed change and the credits it used. `OPENMERIT_VIKTOR_URL` (default `https://api.viktor.com`) and `OPENMERIT_VIKTOR_POLL_MS` (20 s) point the tests at a fake Viktor.

## Checks

`npm run check` typechecks and runs the tests in `test/` (about 110 s on a 2-CPU orb). `test/conformance.test.ts` runs openmerit-core's Scout (through the repo scan and eval command connections) and the cloud job (through the agent bundle) on the same fixture tickets and the same fake models, and checks that they measure the same models, rank the same Top 3, ask the same approval question and spend the same. `test/viktor.test.ts` connects a fake Viktor workspace, evaluates its task end to end and approves the change. The tests start the app in a child process on a local Rivet engine, with test sign-in, fake Stripe and a fake OpenAI-compatible server for OpenRouter and customer endpoints: no credential and no paid call. They include a job that waits on its label check across a SIGKILL of the app, a measure step replayed after a crash whose spend counts once, a job that a new version's drain moves in the middle of a measure step (`RIVET_NODE_VERSION` 1, then 2 on the same engine), and a job whose step fails for good. The checks need openmerit-core's packages installed too (`npm ci` in `openmerit-core/`), since its sources resolve them there. The `cloud` CI job also builds the image (`docker build -f cloud/Dockerfile .` from the repository root) and loads `src/app.ts` in it, since the image holds only the openmerit-core sources the app imports: a new import from openmerit-core needs a `COPY` in the Dockerfile and a line in `.dockerignore`.

To run it by hand against a local engine: `TEST_STORAGE=$(mktemp -d) TEST_ENGINE_PORT=23400 node test/serve.ts`.

| `POSTHOG_PROJECT_TOKEN`, `POSTHOG_HOST` | fixed setting, setting | PostHog analytics (`src/analytics.ts`): `mcp_tool_called` for each MCP tool call, from the MCP handler, and `run_completed` once per job when it ends, from the job actor, with the trigger (`app`, `mcp` or `watch`). Events carry the Clerk user and organization IDs, the tool or status, `ok` and durations: never arguments, results, bundles or error text. Without a token nothing is sent. `npm run deploy` always sets the production OpenMerit project's public token, written in `scripts/deploy.ts`, and never copies this environment's token, which is the Internal project's. `POSTHOG_HOST` defaults to `https://us.i.posthog.com`; the deploy does not set it, and the tests point it at a local fake |

The cluster sets `RIVET_ENDPOINT`, `RIVET_TOKEN` and `RIVET_POOL` on every deploy; do not set them.

## Deploying

Every deploy and secret change needs the owner's approval. `npm run deploy` follows the repository's `scripts/deploy.ts` rules: a clean checkout whose HEAD is on `origin/main` and passed the `verify` and `cloud` CI jobs with no other job failed (jobs still queued or cancelled, such as the npm package's macOS runs, do not hold it up), then a receipt in `.deploys/cloud/` with the rollback command. The deploy writes the commit into the image (`src/build.json`, gitignored), which `GET /health` reports as `commit`, and waits up to 5 minutes for the origin to report the commit it rolled out three times in a row; otherwise it fails, since an older build may still be answering. A rollback with `--build` expects the commit its receipt names. Builds before this check report no commit. `npm run deploy -- status` prints the commit the origin serves. It needs `RIVET_CLOUD_TOKEN` (the cluster's `rivet_cluster_…` token, which selects its organization, so `RIVET_ORG` stays unset; the engine's admin token does not reach the Cloud API) and Docker. `RIVET_CLUSTER` is the cluster's name, `openmerit`; its slug `openmeritdr2i` is only in the origin. A secret that is not on the cluster yet, such as `STRIPE_WEBHOOK_SECRET` before the webhook is registered, is left out of the pool, and the feature that needs it answers 503.

```sh
npm run deploy -- secrets          # copies the secrets above that this environment has to the cluster, by name
npm run deploy -- --dry-run        # prints the rivet deploy command
npm run deploy                     # builds cloud/Dockerfile, uploads it and rolls the pool onto it
npm run deploy -- --build <id>     # rolls back to an earlier build, without rebuilding
npm run deploy -- status           # read-only: the last receipt and what the origin answers
```

A cluster token cannot create the runner pool. The pool `default` (`us-east4`, one e2-small node on the free plan) was created on 18 November 2026 by one rollout signed in with `rivet login` as the cluster's owner; later deploys only roll it onto a new build and work with the token. If the pool is ever deleted, create it the same way, then `rivet logout`.

After the first deploy, set `CLOUD_APP_ORIGIN` to `https://openmeritdr2i.onrivet.dev` in `wrangler.domains.jsonc` and deploy the router, and register the Stripe webhook endpoint for `https://openmerit.ai/api/stripe/webhook`.
