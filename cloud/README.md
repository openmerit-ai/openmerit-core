# OpenMerit cloud

The Node.js app behind `claude mcp add --transport http openmerit https://openmerit.ai/mcp`. It runs as a Rivet Cloud hosted actor node on the Rivet Cloud cluster `openmerit` (slug `openmeritdr2i`, region `us-east4`), served at `https://openmeritdr2i.onrivet.dev`. openmerit.ai's domain router (`demo/domain-router.mjs`) proxies `/mcp`, `/.well-known/oauth-protected-resource` and `/api/*` to it when `CLOUD_APP_ORIGIN` is set.

Not released: nothing here is deployed until the deploy below runs.

## What it serves

| Path | Does |
| --- | --- |
| `POST /mcp` | MCP over streamable HTTP, stateless per request, with the tools `openmerit_recommend`, `openmerit_result`, `openmerit_answer`, `openmerit_tasks`, `openmerit_eval` (a task's eval files for the repository, and recording that the agent wrote or removed them) and `openmerit_retire`. Each call needs a Clerk OAuth access token whose audience is `https://openmerit.ai/mcp`; without one it answers 401 with `resource_metadata`, which starts the client's Clerk sign-in. No tool takes an API key |
| `GET /.well-known/oauth-protected-resource` (and `/mcp` after it) | RFC 9728 metadata naming Clerk (`https://clerk.openmerit.ai`) as the authorization server |
| `/api/*` | The account API for app.openmerit.ai, with Clerk session tokens: `me`, `projects`, `me/subscriptions`, `me/case-writer`, `tasks`, `tasks/:id/eval`, `tasks/:id/run`, `tasks/:id/retire`, `eval-drafts`, `runs`, `endpoints`, `repos`, `guardrails`, `spend`, `billing/checkout`, `billing/portal`, `account/export`, `account` (DELETE), `disconnect`. The shared contract lists each. Deleting a task (`DELETE /api/tasks/:id`) or the account needs the admin role and a first-factor verification in the last 10 minutes (the Clerk session token's `fva` claim); otherwise the 403 body is Clerk's reverification error, which Clerk's `useReverification` turns into its re-verify prompt and a retry. Deleting a task erases its task and job actors, reports, share links, task-level guardrails and index row, and refuses with 409 while a run is computing. A job whose start failed partway, such as in a Rivet outage, has no job actor and never computes: starting it marks it failed and says nothing was charged, and a later start or delete marks failed any such job still queued after `OPENMERIT_ORPHAN_AFTER_MS`, so it holds no concurrent-job slot and does not block the delete. Its runs leave every listing but keep a content-free row, as the spend ledger does, so deleting gives back no evaluations or spend. `GET /api/tasks/deleted` lists who deleted which task and when |
| `POST /api/stripe/webhook` | Stripe only, signature-verified. The source of truth for an account's plan |
| `GET /api/r/<job>.md` | A report as Markdown, for the account's members and for agents with their MCP token. `POST /api/runs/<job>/share` makes a public link, `/api/share/<token>.md`. The token carries the account ID sealed with `OPENMERIT_KEY_ENCRYPTION_KEY` (AES-256-GCM), so a link does not show the organization's ID, and one that does not decrypt is a 404 that opens no actor |

The account is the token's Clerk organization (`org_id`). Clerk's OAuth access tokens for `/mcp` carry no role, so no MCP tool depends on one, and an MCP call keeps the member's role as the web app's session token last recorded it. A token without one is refused with an error that tells the user to create or choose an organization; the app never guesses an account.

## Actors

- `account` (key: Clerk organization ID), in SQLite: the plan from Stripe, members, endpoints with keys encrypted by `OPENMERIT_KEY_ENCRYPTION_KEY` (AES-256-GCM, the account ID as associated data), GitHub repositories with their tokens encrypted the same way and their last review (see GitHub repositories), guardrails at the environment, agent (`environment:agent`) and task levels, the spend ledger, jobs, tasks and reports. It checks the plan, jobs per hour and concurrent jobs at every job start, and reserves spend against the job's budget, the guardrail caps and the monthly caps before every model call.
- `task` (key: account and task ID): the latest bundle, the labels the user gave, the written cases the user approved, the last result and the watch schedule. Every task is watched: from its first job it checks the catalogue on its schedule and when the catalogue changes, and starts a watch job when the catalogue version is newer than its last run's and the task's state is `watching`. The account computes the state when it is read, from what it stores, so it is never stale:
  - `frozen`: the `watch: false` guardrail, at the environment, agent or task level, keeps a validated model. A lower level can set `watch` either way.
  - `idle`: no `openmerit_recommend` call for the task in `OPENMERIT_IDLE_DAYS` (default 30), so watch runs stop spending OpenMerit's money on unused tasks. `idleSince` says when. Watch runs do not keep a task active; the next recommend call does.
  - `retired`: the coding agent called `openmerit_retire` after removing the model call from the code, or someone retired it in the app. It disarms the schedule and keeps the runs and reports; the next recommend call for the task brings it back.
  - Retired is reported before frozen, and frozen before idle. `/api/tasks` returns `state`, `idleSince` and, for older clients, `watching` (`state` is `watching`). Deleting a task is separate from all of these.
- `job` (key: job ID): the workflow Source ▶ Cases ▶ label check ▶ Models ▶ Ranking ⇄ Grading ▶ Agent eval ▶ Action. The workflow is openmerit-core's task job (`openmerit-core/src/job/workflow.ts`, `runTaskJob`), with its pool (`job/pool.ts`) and report (`job/report.ts`), which every host runs. `src/actors/job.ts` is the cloud's host for it (`JobHost`): the account actor's guardrails, accepted eval, endpoints and ledger, the task actor's labels and results, the catalogue actor, a member's subscription as case writer, and the `run_completed` event.
  - **Cases** are the bundle's examples, then up to 12 cases that `openmerit/ranking`'s case writer writes on OpenMerit's OpenRouter key (`OPENMERIT_CASE_WRITER_MODEL`). Writing them is billed to the job. When the bundle has a task spec (`input`, `steps`, `criteria` and `guardrails`; see `openmerit_recommend`'s schema), the writer works from it and tags each written case `typical`, `edge` (about a quarter) or `guardrail` (about a quarter, when the spec has guardrails). A task's later runs, such as watch jobs, reuse the written cases the user approved and write none.
  - **The label check** waits on the job's queue for `openmerit_answer`. It asks `label_<case>` for each example without an expected answer, and `label_check` (a multi-select) for the written cases: an unticked case is dropped. Each option shows the case's input and expected answer in full (inputs are cut only past 1,000 characters).
  - **Ranking** is `openmerit/engine`'s `evaluateTask`, the policy the CLI runs (see openmerit-core's README, steps 6 and 7), over `openmerit/ranking`'s `createMeasure`, which runs every case in Pi's agent loop: single calls and agents alike, with the bundle's tools answered from mocked results. The current model runs every case three times (the `repeats` guardrail). A screen runs on every case the current model passed in every run, or on 20 of them drawn inside a recorded step when it passed more, the same ones for the same eval since each case's place in the draw is a hash of its content; a model that misses exactly one is screened once more on that case. A case whose model call failed or timed out runs once more before it counts; a candidate whose call fails again is unavailable, not screened out. The finalists run every case three times, and challengers are screened before their full runs. The provisional pick the agent was told, which is the task's last measured pick when it has one, is screened and measured too when no qualified model costs less per call than the current one, or when its list price is under the cheapest qualified model's, so a run does not replace the last pick with a dearer model without measuring it again. Each screen and each repeat is its own measure step with its own ledger keys. A model qualifies when it passes at least as many case runs as the current model and fails none of the cases the current model passed in every run in most of its own runs (`shortfall: "regressed"`, with the cases in its note). The Top 3 are the qualified models, cheapest per call first; the pick is the cheapest of them that costs at least 10% less per call than the current model (`MIN_SAVING`), else the result is `keep_current`, and the pick carries `paybackCalls`, the calls its saving takes to repay the run's spend. `openmerit_recommend` answers with an `estimate` before anything is measured: case runs, dollars (capped at the budget per job) and a range of minutes for one search, from the pool and the catalogue's prices, and `rounds`, the most searches the job may run: 3 in a first run that a person grades, since each round whose grades write the eval again searches again, else 1. Models within one case per run of the current model's pass count are listed as `nearMisses`. A job that started measuring before this policy was deployed ends `failed` when it next wakes, asking to rerun it, since its recorded steps do not replay under the new one. The pool is the catalogue's models with a capability index (ECI) on OpenRouter, which leaves the others out with a notice, plus the models the customer lists on their own endpoints, which without an ECI are measured as challengers. `progress.planned` estimates the measure steps (the current model's runs, about log₂ of the pool in screens, the finalists' runs, and each challenger's screen and runs) and is exact once the search ends. While a measure step runs, `GET /api/runs/<job>` also returns `live`: the candidate, its passes after each case of that step, the current model's pass rate so far and an estimate of the minutes left at the pace of the steps already done, for the app's live chart; it is null between steps and once the job ends. When the budget refuses a challenger, the remaining challengers are left out with a notice and the job finishes on the finalists. A candidate whose measure step still fails after its three attempts, such as on a deadline, is skipped as unavailable, and the search goes on. A budget refusal before the finalists are measured stops the job with a `stopped` report of what was measured. Text answers are graded by a fixed judge (`OPENMERIT_JUDGE_MODEL`), whose calls count in the job's spend but not in a candidate's cost per call. Its rubric is the task itself, the bundle's description and input, with one check per criterion and per guardrail; any failed check fails the case. For a task with tools, the judge reads the whole run in order: what the model said, each tool call with what the tool returned, then the final answer, so facts taken from a tool's result count as grounded. Label and JSON answers that match also go to the judge for the guardrail checks alone when the spec has guardrails. A failed case keeps the grader's redacted one-sentence reason, and the report lists up to 20 of the current model's failed cases with their kind and reason (`failedCases`), and its pass rate per kind of case (`baselineByKind`). **The floor:** when the current model passes under 80% of its case runs, the eval cannot tell models apart, so nothing is screened. In a run that grades (below), a person then grades the current model's answers, which says whether the eval or the model is wrong; otherwise the job ends `done` with the result `below_floor`, no pick, no approval question and an `ask_agent` fix to correct the bundle from the failed cases. Each model call's ledger key is the job, the step, the candidate and the case, so a step that Rivet replays after a crash counts no spend twice.
  - **The grading loop** (openmerit-core's `eval/loop.ts`, the state machine the CLI's Scout runs). It runs in a run a person started (an MCP call or the app, not a watch), in a task's first run, before it has an accepted eval, on cases OpenMerit wrote, when OpenMerit's OpenRouter key is set. After each search the job asks one question per sampled answer, `grade_<task>_r<round>_<n>`: up to six of the current model's answers from its first run and six of the pick's (else the best measured finalist's), failed ones first, each with its input, tool calls and OpenMerit's grade, redacted and cut short. A person answers `good` or `bad`, optionally with a note after a colon (`bad: <why>`), through `openmerit_answer`, which tells the coding agent never to grade them itself, or on the run's page at app.openmerit.ai (`POST /api/runs/<job>/answers`); the job records who sent them. A grade it cannot read is reported in the notices and asked again.
    - **Agreement on every answer accepts the eval** as version 1 (`acceptFirstEval` with source `grading`, the person who graded and the bar), in place of the acceptance a first run makes without grading. Later runs of the task, watch jobs among them, measure on it unchanged against the same bar without asking.
    - **A disagreement writes the eval again:** the reviser rewrites the spec's criteria and guardrails from the grades and notes, and the case writer writes the written cases again (the examples and their labels stay), both on OpenMerit's key, metered in the job's ledger. It stays in the job until the person agrees with it, and the search runs again on it from scratch. After three rounds without agreement the job ends `done` with the result `not_accepted`, no pick and no accepted eval.
    - **Marking the current model's own answer wrong changes the bar** (`criteria`): the search runs once more on a wide pool, every eligible model whatever its price, and a model qualifies when it passes every guardrail and step check on every case and each criterion on at least 90% of them (the `criteriaPassRate` guardrail). The pick is the cheapest model that meets them, even when it costs more than the current one, and the result's `grading.summary` says so, such as "Your current model fails 1 of your checks (G3); the cheapest model that passes them is Y, at $0.40 more per 1,000 calls." A task with no criteria, such as a label task, has one: the expected answer.
    - The result's `grading` gives the rounds, whether the eval was accepted, the bar, the current model's failed checks and the summary. Jobs that started ranking before the loop was deployed rank once, as they began.
  - **Agent eval** is the engine's `checkAgent` rule. A task whose bundle offers tools is an agent: its pick, then the next cheaper qualified models, run the task's cases again end to end in Pi, and each case passes on its whole transcript (`openmerit/ranking`'s `flow` grader: the answer passes, it calls no tool the task does not offer, it fixes any call the tool's schema or mocked result refused by calling that tool again, and it takes the spec's `required` steps, in the `after` order where the spec gives one). The step checks show in `basedOn` as S1 and up, beside the judge's C… and G… checks. A case with no mocked result for one of the task's tools is left out for every model, with a notice, an `ask_agent` fix and the result's `invalidCases`, since the eval cannot run it. A switch passes when it passes at least as many cases as the current model and meets the agent's minimum pass rate. An agent made of several tasks with their own models (the bundle's `agent`) is not checked yet: no source provides its chained cases, so it reports that the agent has no eval; **Action** writes the edit and the report. The pool rule, the provisional pick, the result (Top 3, near misses, pick) and the edit are `openmerit/engine`'s (`eligible`, `provisionalPick`, `taskResult`, `proposeEdit`), which the CLI uses too. The edit replaces only the model ID string literal in each code ref's `spelling`, keeping its quotes, a `provider:` prefix and the code around it, such as an environment variable it falls back from. On OpenRouter it writes the full catalogue ID, and on a customer's endpoint the name that endpoint uses. A ref with no model literal, or a literal that names another model than the current one (a fallback), gets an instruction instead of or beside the edit. The edit comes from the agent bundle connection's Change port (openmerit-core's `src/connectors/agent-bundle.ts`). The result also has `basedOn`, the evidence each decision used by the engine's quality rule (for example "Grader: the expected labels of your examples, from agent-bundle"), and `approval`, the question to ask the user before applying the edit, worded as the CLI's Configure question; the report shows `basedOn` under "Based on". `GET /api/runs/<job>` returns the report with the same `reason`, `cheaperThanCurrent`, `nearMisses`, `basedOn` and `approval` as `openmerit_result`. A result's `fixes` say what resolves some of its `notices`, each naming its notice by its text: `raise_budget` (the job's own budget refused a call; it suggests twice the budget, rounded up to whole dollars), `rerun`, `open` (a page at app.openmerit.ai, such as Connections or a task's or agent's guardrails) and `ask_agent` (an instruction only the coding agent can carry out, such as adding labelled examples). `openmerit_result` prints each as a `Fix:` line under its note. `POST /api/runs/<job>/rerun`, and `openmerit_recommend` with `job_id` instead of a bundle, run that job's task again on the bundle the task last ran on, with its environment and agent; `budgetUsd` (MCP: `budget_usd`, at most $1,000) first sets the task's `budgetUsd` guardrail, keeping its other task-level settings. A rerun starts like any run, within the plan and the spend caps.
  - **Across deploys and crashes** the job resumes from its last completed step. A deploy drains the old version's actors: a step it interrupts, such as a measure step waiting on a model, runs again on the new version with the same ledger keys, so its calls are counted once, and a call cut off mid-answer counts at its reservation, since the provider may have billed it. A step that fails for good ends the job `failed`, with the error, a notice and a report of what it measured; a failed job is not charged an evaluation.
- `catalogue` (one): openmerit-core's bundled catalogue, refreshed daily when the app has a refresh source.

The app imports `openmerit/engine` (through `src/engine.ts`) and `openmerit/ranking` from openmerit-core's source, which the image copies.

## Projects

An account's projects split its tasks, runs, guardrails, model endpoints and GitHub repositories; the plan, members, spend caps, the ledger and billing stay the organization's. Every account has the `default` project, which holds everything it had before projects, can be renamed and cannot be deleted. Tasks in the default project keep their IDs; a task in another project has its own ID, so the same task name in two projects is two tasks.

- **The API.** `GET /api/projects` lists them with what each holds; admins `POST /api/projects` (`{name}`, unique in the account ignoring case, at most 64 characters and 50 projects), `PUT /api/projects/:id` to rename and `DELETE /api/projects/:id`, which deletes the project's endpoints, repositories and guardrails and is refused while it has tasks. Every other `/api` route works in the project the `X-OpenMerit-Project` header names, or the default project without one; an unknown project answers 404. A task's guardrails are its own project's, whichever project the request names.
- **Repositories place calls.** A GitHub repository belongs to one project; adding it to another is refused until it is removed. `openmerit_recommend` runs in the project whose repository the call's `environment` names (`owner/repo`, ignoring case), else the default project, unless its `project` argument names one by name or ID. A rerun keeps its job's project. `openmerit_tasks` names each task's project once the account has more than one.
- **Older accounts and jobs.** The account actor's migration adds a `project_id` (default `default`) to endpoints, jobs, tasks, deletions and repositories and rebuilds the guardrails table keyed by project. Jobs and tasks recorded before projects run in the default project.

## Evals

The cloud is the source of truth for each task's eval: its spec (description, input, steps, criteria and guardrails, the part of the bundle the judge checks) and its cases. An eval is reviewed until it is right for its task, then accepted, and stays as accepted until the task itself changes. The account actor keeps one row per task in `evals`: the accepted eval and any draft under review. The code is in `src/actors/account.ts` (`evalGate`, `acceptFirstEval`, `acceptEval`, the drafts), `startJob` in `src/start.ts` and the job's cases step.

- **Accepted.** A task's first run writes its cases, and the answers to its label check make the eval it accepts as version 1, recording who wrote it (OpenMerit's key, a member's subscription or the agent's examples alone). Approving a repository review's draft accepts version 1 too. In a first run a person started on cases OpenMerit wrote, the grading loop is that review instead: the person grades sampled answers, and the run accepts the eval as version 1 (source `grading`, by the person who graded, with the bar they graded to) only once they agree with it on every answer; an eval it wrote again from their grades lives in the job until then. A run that stops first, or ends `not_accepted`, accepts nothing, so the next run writes its cases again. An eval accepted against the criteria keeps that bar in later runs and in its repository copy's `eval.json`. Later runs and watch jobs measure on the accepted eval unchanged: its cases, and its spec in place of the one the coding agent sent, with a notice when they differ. They ask no label check, write no cases and add no examples; examples the agent sends that the eval lacks are named in a notice. Each job records the version on its row (`evalVersion` in `/api/runs`) and in its report; the app warns that runs on different versions are not comparable, which can only happen after a re-acceptance.
- **Reopened.** The accepted eval records the prompt, tools (without their mock results) and output it was accepted for. When the coding agent sends the task with a different one, `startJob` refuses the job, saying what changed, and reopens the eval as a draft (`reason: task_changed`): the accepted spec and cases with the bundle's new examples, and the new bundle. A person can also reopen it (`POST /api/tasks/:id/eval/revise`, `reason: revise`). While a draft is open the task's state is `review`: no run or watch job starts, and Review evals lists it. Edits save over the draft (`PUT /api/tasks/:id/eval/draft` with `{spec, cases, base}`; a save since `base`, the draft's `at`, refuses with 409), and no earlier text is kept. `POST /api/tasks/:id/eval/accept` accepts it, with any last edits, as the next version and moves the task onto the changed bundle; runs and the watch resume. `DELETE /api/tasks/:id/eval/draft` discards a revision; a changed task's draft cannot be discarded, since its accepted eval no longer fits.
- **The repository copy.** The coding agent writes the accepted version to `.openmerit/evals/<task>/` (`bundle.json`, `cases.json`, `eval.json` and a `MANAGED.md` saying to revise it in the app) with the `openmerit_eval` tool, after asking the user, and reports the version it wrote (`action: synced`); only the accepted version is accepted. `openmerit_tasks` and a finished `openmerit_result` say when the copy is behind, and `openmerit_tasks` says when a draft waits for review. Scout runs a managed copy as it is and never reviews the task or writes over it.
- **Drafts.** A repository review offers each eval Scout wrote in the repository (`.openmerit/evals/*/bundle.json` and `cases.json`, without `MANAGED.md`) and each task spec the review writes as a draft in the repository's project: `GET /api/eval-drafts`. Approving one (`POST /api/eval-drafts/:id/approve`, optionally with an edited `{spec, cases}`) creates the task, not run yet, with the draft accepted as version 1; it neither watches nor spends until its first run, which `POST /api/tasks/:id/run` or `openmerit_recommend` with `task_id` starts. Dismissing one (`DELETE /api/eval-drafts/:id`) clears its content. A later review offers neither again, nor a task the project already has.
- **Retire or delete.** `POST /api/tasks/:id/retire` stops the watch and keeps the eval, which stays in Your data and the export. Deleting a task deletes its eval and any draft; its repository copy stays until the coding agent removes it, which `openmerit_tasks` asks it to offer until it calls `openmerit_eval` with `action: removed`.

## Members' subscriptions

A member can sign in to their own ChatGPT (Plus or Pro) plan on app.openmerit.ai's Account settings and choose it to write the cases of the runs they start, instead of OpenMerit's OpenRouter key. The code is in `src/subscriptions.ts` and the `user` actor (`src/actors/user.ts`), one per Clerk user and the same in every organization they belong to.

- **The sign-in** is the one pi's `/login` uses (pi-ai's openai-codex OAuth client), a device code: `POST /api/me/subscriptions/chatgpt` returns the code to enter at `auth.openai.com/codex/device`, and the page calls `POST /api/me/subscriptions/chatgpt/poll` until OpenAI says it was entered (15 minutes). `DELETE /api/me/subscriptions/chatgpt` forgets it, and `PUT /api/me/case-writer` with `{writer}` (`openmerit` or `chatgpt`) picks who writes the cases; only a connected subscription can.
- **No Claude sign-in.** Anthropic does not let other developers offer a Claude login in their apps, store its tokens or send requests as Claude Code, so the app has none. A hosted Claude plan would have to run the unmodified Claude Code under the member's own login.
- **Tokens** are encrypted with `OPENMERIT_KEY_ENCRYPTION_KEY`, with `user:<id>` as associated data. No list, page or export returns them; they leave the user actor only for the job's memory. A token within 10 minutes of expiring is renewed first; a renewal that fails is shown on Account settings and the job writes its cases on OpenMerit's key with a notice saying so.
- **What they do.** Only the case writer moves to the subscription, through pi-ai, which sends the requests as Codex does (`OPENMERIT_CODEX_SUBSCRIPTION_MODEL`, default `gpt-5.6-terra`). Those calls are billed by the member's plan and enter no ledger. The judge stays on OpenMerit's key so every candidate is graded the same way, and candidates are measured on OpenRouter and the project's endpoints as before. Watch runs reuse approved cases and write none.
- **Terms.** OpenAI lets hosted products use a ChatGPT plan only through its Sign in with ChatGPT partner program; until OpenMerit is approved, the app uses Codex's client, which OpenAI may restrict.

## GitHub repositories

An account adds the GitHub repositories whose code OpenMerit reviews, on a project's settings page at app.openmerit.ai or with `POST /api/repos` and `{"url": "https://github.com/acme/app"}`. The code is in `src/github.ts`. OpenMerit only reads. It sends GitHub only GET requests and git's fetch, and it never pushes, opens a pull request or writes to a repository.

- **Public repositories** are added by their URL alone. The app accepts `https://github.com/owner/repo`, with or without the scheme, `.git` or a path such as `/tree/main`, and `git@github.com:owner/repo.git`. No other host is accepted.
- **Private repositories** need `token`: a fine-grained personal access token whose repository access covers the repository, with Contents: Read-only. A classic `ghp_` token is refused, since it can write to every repository its owner can, and so is anything that does not start with `github_pat_`. OpenMerit cannot see a fine-grained token's other permissions, so the app asks for Contents: Read-only on only the repositories OpenMerit reviews. The token is encrypted with `OPENMERIT_KEY_ENCRYPTION_KEY`, as endpoint keys are. Lists show only its last four characters, and the export leaves it out. Adding the repository again replaces its token.
- **Through GitHub sign-in.** Clerk's GitHub connection is the OpenMerit GitHub App (`OPENMERIT_GITHUB_APP_SLUG`, `openmeritai`): Contents and email addresses read-only, expiring user tokens, no webhook. Clerk only signs the member in. `GET /api/github` gets the member's GitHub token from Clerk (`getUserOauthAccessToken`, which renews it when it expires after 8 hours) and lists `GET /user/installations` and each installation's repositories: GitHub answers only this app's installations, and the token reaches only repositories that both the member and an installation reach. Without a GitHub sign-in it answers `signedIn: false` and the install link, `https://github.com/apps/openmeritai/installations/new`, with no GitHub call. app.openmerit.ai's Coding agents page (`/connections/`, the app's Setup URL, which GitHub returns to with `installation_id` and `setup_action`) lists them, links GitHub to a Google sign-in with Clerk's `createExternalAccount`, and adds one with `POST /api/repos` and `{url, via: "github"}`. The repository keeps the member's Clerk user ID (`githubUser`, `access: "github"`) and no token. Every review gets the member's token from Clerk again and gives it to git as the private-repository token is given, never in argv or `.git/config`. When that member unlinks GitHub or leaves, the review fails and says to add the repository again with another member's GitHub sign-in or a token. Reviews run only when someone asks for one, so no installation token, App private key or new secret is needed; reviewing without a member, such as on a schedule, would need them.
- **Access check.** Adding a repository first calls GitHub's free REST API: `GET /repos/{owner}/{repo}` (metadata, default branch and size) and, with a token, `GET /repos/{owner}/{repo}/commits?per_page=1`, which needs Contents read. The answer says what to fix: no public repository by that name, a token that cannot see the repository or cannot read its code, an expired token, a repository over the size limit, or GitHub's rate limit. Without a token, GitHub allows 60 of these calls an hour for the node's address, shared by every account. When that limit is used up, GitHub answers 403 or 429, and adding a repository says "GitHub's limit for checks without a token is used up; try again after 14:05 UTC", with the time from GitHub's `x-ratelimit-reset`. A refused check counts no review against the account's hourly limit. Review again clones over git without a REST call, so the limit does not stop it.
- **The clone.** Once a repository is added, and on `POST /api/repos/:id/review`, the account actor queues a review and runs it after the request returns. The review shallow-clones the default branch (`--depth 1 --single-branch --no-tags`, no submodules or LFS objects) into a new temporary directory on the cloud node. It stops at `OPENMERIT_REPO_MAX_MB` on GitHub and on disk and at `OPENMERIT_REPO_CLONE_SECONDS`. At most two clones run at once on a node. git gets only `PATH`, an empty home directory and the token, which goes in an environment-only config entry, not on the command line, in the remote URL or in `.git/config`. It allows only HTTPS, runs no hooks, and checks symlinks out as plain files, so reading the checkout never leaves it. The `.git` directory is deleted once the commit is read, and the whole directory is deleted when the review ends, whether it succeeded or failed. Nothing in the repository runs.
- **The review** (`reviewCheckout` in `src/github.ts`) takes the checkout and returns task specs. It runs openmerit-core's repository scan (`scanRepo`), which lists the model calls, then openmerit-core's review prompt (`reviewRepo` in `openmerit-core/src/review/`) on the application's calls, with `reviewer` `review`. The reviewer model (`OPENMERIT_REVIEWER_MODEL`) runs on OpenMerit's OpenRouter key through openmerit-core's harness: one call maps the calls to tasks, then one call per task writes its spec (input, steps, criteria, guardrails, prompt, tools with mocked results, output and examples), in `tasks` as openmerit/ranking's `TaskBundle`, the shape `openmerit_recommend` takes. The model reads the checkout only through Pi's read-only tools (read, grep, find and ls, which run ripgrep and fd), and the harness refuses any path outside the checkout after resolving symlinks. Nothing in the repository runs. The reviewer gets no secret but OpenMerit's OpenRouter key, and rg and fd get none (see Checks). A review stops at `OPENMERIT_REVIEW_BUDGET_USD` ($2), checked before each request and as each call reports its cost, and at `OPENMERIT_REVIEW_MINUTES` (15). A task whose spec was not written, because the review stopped or the reply failed, is listed in `unmapped` with the reason, and the listing is kept. Without `OPENROUTER_API_KEY` the review is the scan alone, with `reviewer` `scan` and no specs. The review keeps only the application's code: a usage in a test, spec, mock, fixture, recorded response, snapshot, doc or saved result (openmerit-core's `isSupportFile`) is neither listed nor reviewed, so no task spec is written from test code. Examples, scripts and demos stay, since in many repositories they are the application. `supportCalls` counts the calls left out, and `notListed` says so, such as "3 more in tests, fixtures or docs, not listed"; a repository whose calls are all in tests reads "No model calls in application code".
- **What is kept.** The account keeps the repository's name, whether it is private, its default branch, the token, and the last review: the commit, the file count, the models the code names with how many calls name each, up to 200 model calls, each as a file, line and model ID, or the expression or environment variable that picks it, and the task specs. A spec holds what the reviewer wrote from the code: the call's prompt in the code's words with placeholders, its tools' schemas and mocked results, its output schema or labels, up to 10 examples from the repository's tests or fixtures, and each model call's file, line and source line (`codeRefs`). No other source line and no file is kept. The review's prompts and the files the model reads go to the reviewer model through OpenRouter, as a job's cases go to the models it measures. A failed review keeps the last one that finished and the error. `DELETE /api/repos/:id` deletes the repository, its token and its review; a review still running then saves nothing.
- **A paid plan.** Adding a repository and every review, the first and each Review again, need a plan that Stripe says is active or trialing, the same check every job starts with (`planRefusal` in `src/actors/account.ts`). Without one they refuse with the jobs' wording, "This account has no active OpenMerit plan. Subscribe at https://app.openmerit.ai/plan/, then try again." (`POST /api/repos` with 400, `POST /api/repos/:id/review` with 402), before any GitHub call, clone or spend. There is no free cloud plan; the self-hosted CLI is the free option. Repositories added while an account had a plan stay listed with their last review, and can be removed, but not reviewed again until it has one.
- **Spend.** A review's model calls are OpenMerit-paid spend in the account's ledger, under the key `review/<repo>/<requested at>`: its budget is reserved against the monthly OpenMerit-paid cap before the clone, which refuses the review when the cap has no room, and settled at what the calls cost once it ends (the whole budget when Pi does not know the model's price). A clone or scan that fails releases it. A review cut off by a node stop keeps its reservation counted, since what it spent is unknown. `GET /api/spend` and the account export include these rows. A review is not one of the plan's evaluations: whether it should be is undecided, and `EVALUATIONS_PER_REVIEW` in `src/actors/account.ts` (0) is the one place to change it; at 1, each settled review counts one in the plan's period.
- **Limits.** Adding, reviewing and removing need the admin role; members see the list. An account holds `OPENMERIT_REPOS` repositories (20) and starts `OPENMERIT_REVIEWS_PER_HOUR` reviews an hour (20). A review that a node stop, such as a deploy, cuts off shows as failed once it is past the clone timeout plus `OPENMERIT_REVIEW_MINUTES` and 5 minutes, and can be started again.

Running the customer's own eval in the cloud, which needs a VM, comes later.

## The user's decision

`openmerit_result` gives a picked result's `approval`, the question to ask the user before applying the edit, with the ID `configure_<task>`. It tells the coding agent to ask it, apply the edit if the user says yes, and send the answer back with `openmerit_answer` and `{"configure_<task>": true}` or `false`. The account records the decision in its `decisions` table: the job, the task, approved or declined, the change (such as `openai/gpt-5.4 → openai/gpt-5-mini (openrouter)`), the Clerk user ID with the name and email Clerk has for them, and when. The first decision on a job stands; a second answer is refused with the one recorded. An approval also moves the task onto the pick: its bundle's current model and endpoint become the pick's, and its code refs' spelling becomes the edited line, so the next watch run measures the pick as the current model. A decline changes nothing but the record.

`openmerit_tasks` and `GET /api/tasks` show each task's latest decision, and `openmerit_result` and `GET /api/runs/<job>` show the job's. app.openmerit.ai shows the decision on the task and the run, or that the coding agent asks before applying the change; the app has no approve button. Deleting a task deletes its decisions, and the account export includes them.

## Checks

`npm run check` typechecks and runs the tests in `test/` (about 110 s on a 2-CPU orb). `test/conformance.test.ts` runs openmerit-core's Scout (through the repo scan and eval command connections) and the cloud job (through the agent bundle) on the same fixture tickets and the same fake models, and checks that they measure the same models, rank the same Top 3, ask the same approval question and spend the same. A test runs two tasks through the decision: an approval is recorded once with the user's name, moves the task and its code ref onto the pick, and the next watch run measures the pick; a decline leaves the task as it was. The tests start the app in a child process on a local Rivet engine, with test sign-in, fake Stripe and a fake OpenAI-compatible server for OpenRouter and customer endpoints: no credential and no paid call. A test grades a run's answers: a refused grade is asked again, a current-model answer marked wrong writes the eval again (version 2, source `grading`) and changes the bar to the criteria, agreement in round 2 accepts it, and the next run measures on it without asking. They include a job that waits on its label check across a SIGKILL of the app, a measure step replayed after a crash whose spend counts once, a job that a new version's drain moves in the middle of a measure step (`RIVET_NODE_VERSION` 1, then 2 on the same engine), and a job whose step fails for good. `test/github.test.ts` runs GitHub repositories against a local fake GitHub that serves the REST API and real git over smart HTTP (`git http-backend`): a public repository added by URL, a private one with a fine-grained token, the refusals, a symlink kept as a plain file, a clone stopped at the size and time limits, and no checkout left behind. The checks need openmerit-core's packages installed too (`npm ci` in `openmerit-core/`), since its sources resolve them there. The image installs git, which the GitHub reviews clone with, and ripgrep and fd, which the reviewer's grep and find run. fd is the upstream 10.3.0 release, checked against its SHA-256, since Debian's 8.6 lacks `--no-require-git`, which Pi's find passes. Pi passes rg and fd the whole process environment and looks for them in its agent directory's `bin` before `PATH`, so the image sets `PI_CODING_AGENT_DIR=/opt/pi-agent` and puts two wrappers in `/opt/pi-agent/bin` that start them with `env -i PATH=/usr/bin:/bin`: no secret of the app reaches a search over a customer's code. It sets `PI_OFFLINE=1`, so Pi never downloads a missing binary at run time. A test reviews a repository with a fake OpenRouter reviewer: the specs come from the application's calls only, no test file reaches the reviewer, the cost is settled in the ledger and no evaluation is counted; another stops a review at its budget. The `cloud` CI job also builds the image (`docker build -f cloud/Dockerfile .` from the repository root) and loads `src/app.ts` in it, since the image holds only the openmerit-core sources the app imports: a new import from openmerit-core needs a `COPY` in the Dockerfile and a line in `.dockerignore`.

To run it by hand against a local engine: `TEST_STORAGE=$(mktemp -d) TEST_ENGINE_PORT=23400 node test/serve.ts`.

## Self-hosted mode

`OPENMERIT_MODE=self-hosted npm start` runs the same app for one person on their own machine, with no Clerk, Stripe, PostHog or Rivet Cloud:

- It listens on `127.0.0.1` (`OPENMERIT_HOST` changes it) and starts a local Rivet engine on the next port (`OPENMERIT_ENGINE_PORT`), which keeps its state in the data directory, `~/.openmerit/server` (`OPENMERIT_DATA_DIR`, or `server` under `OPENMERIT_HOME`).
- Sign-in is one token: the first start writes a random token to `<data directory>/token`, readable only by its owner. `/mcp` and `/api` take it as `Authorization: Bearer <token>`, and every request with it is the admin of the one account, `local`; the local engine's admin token is the same. A request without it gets a 401 that names the token file.
- No plan is needed; the jobs-per-hour, concurrent-job, per-job and monthly spend caps still apply. Clerk, Stripe and PostHog settings are ignored, so the Stripe webhook answers 503 and the OAuth metadata names no authorization server.
- `OPENMERIT_PUBLIC_URL` and `OPENMERIT_APP_URL` default to `http://localhost:<port>`. `GET /api/me` reports `mode`.

Teams on a self-hosted server will sign in through OIDC; that is not built yet.

## Deploying

Every deploy and secret change needs the owner's approval. `npm run deploy` follows the repository's `scripts/deploy.ts` rules: a clean checkout whose HEAD is on `origin/main` and passed the `verify` and `cloud` CI jobs with no other job failed (jobs still queued or cancelled, such as the npm package's macOS runs, do not hold it up), then a receipt in `.deploys/cloud/` with the rollback command. The deploy writes the commit into the image (`src/build.json`, gitignored), which `GET /health` reports as `commit`, and waits up to 5 minutes for the origin to report the commit it rolled out three times in a row; otherwise it fails, since an older build may still be answering. A rollback with `--build` expects the commit its receipt names. Builds before this check report no commit. `npm run deploy -- status` prints the commit the origin serves. In an Amp orb, start the Docker daemon first as the root `AGENTS.md` describes; `.agents/setup` installs Docker and buildx. It needs `RIVET_CLOUD_TOKEN` (the cluster's `rivet_cluster_…` token, which selects its organization, so `RIVET_ORG` stays unset; the engine's admin token does not reach the Cloud API) and Docker. `RIVET_CLUSTER` is the cluster's name, `openmerit`; its slug `openmeritdr2i` is only in the origin. A secret that is not on the cluster yet, such as `STRIPE_WEBHOOK_SECRET` before the webhook is registered, is left out of the pool, and the feature that needs it answers 503.

```sh
npm run deploy -- secrets          # copies the secrets above that this environment has to the cluster, by name
npm run deploy -- --dry-run        # prints the rivet deploy command
npm run deploy                     # builds cloud/Dockerfile, uploads it and rolls the pool onto it
npm run deploy -- --build <id>     # rolls back to an earlier build, without rebuilding
npm run deploy -- status           # read-only: the last receipt and what the origin answers
```

A cluster token cannot create the runner pool. The pool `default` (`us-east4`, one e2-small node on the free plan) was created on 18 November 2026 by one rollout signed in with `rivet login` as the cluster's owner; later deploys only roll it onto a new build and work with the token. If the pool is ever deleted, create it the same way, then `rivet logout`.

After the first deploy, set `CLOUD_APP_ORIGIN` to `https://openmeritdr2i.onrivet.dev` in `wrangler.domains.jsonc` and deploy the router, and register the Stripe webhook endpoint for `https://openmerit.ai/api/stripe/webhook`.
