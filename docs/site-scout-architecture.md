## Catalogue identities and catalogue models in Scout — deployed, 26 October 2026

**Deployment receipt:** the owner approved the push and deployment. Commit [3364230](https://github.com/laz-aslam/openmerit/commit/3364230) is on `origin/main`. Publisher `openmerit-scout` moved from `27bd6884-8d8d-4b7c-be7a-1d13d05dd397` to `07118166-8674-4003-83ad-d3150652d6bb`, with schedule `7 0,12 * * *`. No manual run was made; the 12:07 UTC refresh is the first to use it.

Two changes widen what reaches Scout from the D1 catalogue.

**Identity resolution in `scout/catalogue-db.ts`.** `resolveListings` now tries exact keys in this order, and an ambiguous key resolves nothing:
1. the same Models.dev route;
2. a canonical ID, also as a service variant (`:free`, `:batch`, Vercel's `-batch`);
3. the identical provider model ID mapped to one model elsewhere;
4. a link the source itself gives;
5. a Hugging Face repository named for one model, by Models.dev `weights` or by an already-resolved route's `hf_id` (`hf-repo`);
6. the route's model slug equal to exactly one canonical model's slug (`slug-unique`). For example, `accounts/fireworks/models/qwen3-8b` and `Qwen/Qwen3-8B` both resolve to `alibaba/qwen3-8b`.

Models.dev's own unlinked provider entries go through the same tiers against Models.dev itself. Hub crawls keep slugs off, because a repository named like a lab's model may be anyone's fine-tune. On 26 October data, Models.dev's canonical slugs had no collisions.

**Gateway identities.** An OpenRouter or Vercel `lab/model` ID that no tier resolves becomes a canonical model, with basis `openrouter-id` or `vercel-id`. Service variants share it, and routers and `~` aliases never count. The gateways now import before LiteLLM and genai-prices, so those price lists resolve to the new identities in the same run. Each source withdraws only its own models, by basis prefix. Models.dev takes over an ID once it lists it, and a gateway never overwrites another source's model.

**Catalogue models in Scout.** `collect-public-feeds` reads the catalogue once (`loadCatalogue` in `scout/catalogue-routes.ts`). `compileSnapshot` then adds catalogue models before benchmark rows are matched:
- **Which models qualify:** canonical chat models (type unknown, `chat` or `language`, text output) with at least one admitted, priced chat route, that no feed model links to.
- **Possible duplicates stay out:** a catalogue model whose name or ID slug an existing model already uses is left out, because it may be that model under another catalogue ID. Models.dev has such duplicates, for example `deepseek/deepseek-v3.1` and `deepseek/deepseek-chat-v3.1`. So no existing match can become ambiguous.
- **What a catalogue model carries:** it is labelled `listedBy: "catalogue"`, its price is its cheapest route's, and it has creator and release-date facts from the catalogue.
- **Without D1:** the previous generation's catalogue models are kept, and the `catalogue` source is marked failed.

`collect-public-feeds` now calls `addCatalogueRoutes` in `pipeline.mjs`, which uses `scout/catalogue-routes.ts`. It attaches hosted routes from the D1 catalogue to Scout's own models.

**Matching routes to Scout models**
- **Exact identity only:** a Scout model links to a canonical model through its OpenRouter route, its native Models.dev route, or an identical canonical ID. A model with conflicting links gets nothing.
- **Duplicate Scout IDs:** when Scout lists one canonical model under two IDs, its routes go to the measured one, otherwise to the one with more routes.

**Which providers count**
- **Allow-list:** `scout/catalogue-providers.json` lists the reviewed providers, with the owner's decision of 26 October behind it. It has 21 model makers' own APIs and 34 inference hosts, all with a fixed public HTTPS OpenAI-compatible endpoint. Together, DeepInfra, Groq and Cerebras get documented base URLs, because Models.dev lists them under their own SDKs.
- **Excluded:**
  - resellers, routers and gateways
  - coding or token plans
  - local servers and account-templated endpoints, such as Bedrock, Azure and Vertex
  - the ten providers Scout adapts natively

**Which routes count**
- The route must be live, accept text and output only text, and have positive base input and output token prices. Models.dev's price is used first.
- A provider the model already has isn't added again. When a provider lists the model under several IDs, the cheapest is kept.
- The routes form a `catalogue` source. If D1 can't be read, the previous generation's routes are kept and the source is marked failed.

`scout/catalogue-hub.ts` catalogues every model published by admitted Hugging Face organisations. It runs as two refresh steps before offerings are rebuilt, only when the publisher has an `HF_TOKEN` secret.

- **`catalogue-hub-orgs`** collects candidate organisations from three places:
  - authors of `hf_id`s in `cat_listings`
  - Epoch's Hugging Face developer IDs
  - authors of the 1,000 most-downloaded text-generation, image-text-to-text and text-to-image models

  It then checks up to 400 organisation overviews per run, oldest first, and rechecks each weekly. The Hub has no endpoint that lists verified organisations.
- **Admission:** an organisation is admitted when the Hub verifies it, or when a catalogue source names it as a model's home. Several major labs are not verified, including Qwen, Z.ai, Moonshot, MiniMax and LG EXAONE. Unverified organisations that only appear through download rankings are not admitted, and nor are personal accounts.
- **`catalogue-hub-models`** crawls admitted organisations that are due, oldest first, within a budget of 250 pages of up to 1,000 models. Each organisation is recrawled weekly. A run stays near 650 requests, under the Hub's limit of 1,000 per 5 minutes.
  - `cat_hf_models` stores each repository's task, library, dates, popularity, licence, gating, parameter count, lineage (`base_model` relation and repositories) and papers.
  - It links a repository to a canonical model when another source's `hf_id` maps it to exactly one model.
  - Live inference routes become `huggingface:<backend>` listings with their prices.
- **Failure handling:** an organisation is stored whole or not at all. `storeCatalogue` now takes an owner scope, so a crawl withdraws routes and closes prices only for the organisations it crawled. A failed organisation stays due. A rate limit (HTTP 429) stops the step without marking or withdrawing anything.

A local run against the live Hub found 1,033 candidate organisations. After the first 400 checks, 187 were admitted: 62 verified and the rest catalogue-named. ## Refresh memory: smaller documents and ASCII storage — 25 October 2026

The memory failure returned in two steps. 37 of the 50 hourly runs before the twice-daily change failed. `collect-public-feeds` usually failed, and runs that got past it then failed in `interpret-evidence`; a manual run after the first fix below did exactly that. The published records file had grown to 41.4 MB. Research took 19.0 MB of it, across 1,476 records. The 360 benchmarks took 16.5 MB, of which 10.9 MB is per-capability interpretation over the 210 registry capabilities.

Measurement showed that peak memory comes from parsing single large documents, not from holding the parsed data. Parsing one document transiently needs about four to five times its size. The files also contain non-Latin-1 text, so V8 holds each whole document as a two-byte string.

The changes:

- **Research stored separately.** Publication writes research to `catalogues/<id>.research.json` beside the records file, and `store.mjs` `readPublished` loads either part. Collection reads only the records and writes `collected.json` as `{next}` without the previous generation. Research planning reads only research. Evidence interpretation re-reads the published generation, which the refresh lock keeps unchanged until this run publishes.
- **ASCII, piecewise writes.** `putJSON` escapes non-ASCII as `\uXXXX` and serializes large containers piecewise into one byte buffer. Every stored document therefore parses as a one-byte string, and no step builds a whole-document string.
- **Interpretation loads largest first.** It parses the published generation before its own snapshot and releases inputs once `integrateResearch` has copied them. `integrateResearch` no longer deep-clones research records, which it only replaces. The candidate's research goes to `runs/<id>/candidate.research.json`, which staging reads back.

Catalogue content and the publication digest are unchanged, and generations published before the split still load. Escaped JSON parses to identical values, so serving readers are unaffected.

Measured on production generation `e8b5c21256a782acbd45247c34b1fdf9` with recorded feeds replayed and semantic calls stubbed, as the minimum Node heap including R2 byte encoding:

| Step | Before | After (first run) | After (steady state) |
| --- | --- | --- | --- |
| `collect-public-feeds` | 161 MB | 161 MB | 97 MB |
| `interpret-evidence` (no new research) | 219 MB | 144 MB | 118 MB |
| `collected.json` | 62.0 MB | 18.3 MB | 18.3 MB |

"First run" means reading today's single-file, non-ASCII generation, which happens once; its first publication writes the split ASCII format. A scratch end-to-end `runRefresh` ran twice against that generation with an in-memory bucket. Both runs published 392 models, 360 benchmarks and 5,211 observations, with all 1,476 research records in the separate file. Node's figures include runtime overhead absent from Workers, so only the relative change is meaningful. Completed research batches add to interpretation memory in proportion to their size.

**Rollback hazard:** a publisher older than this change reads a split generation as having no research and would publish without it. Roll back only to a version that includes `readPublished`, or first restore research into the records file. Growth remains. Research adds up to 24 records per run, and every capability that research adds is stored on every benchmark's interpretation, so that data grows with capabilities × benchmarks. Compacting the interpretation map saved little peak memory in measurement (131 MB to 127 MB), so the next lever is splitting benchmark records the same way.

The live manifest `e8b5c21256a782acbd45247c34b1fdf9` carried a policy identical to the seed, so the only effective change is the freshness allowance. ## Lifecycle monitoring repair — 24 October 2026

The [existing PostHog dashboard](https://eu.posthog.com/project/315509/dashboard/1044618) removes obsolete setup-artifact filters and retired connected-event dependencies. The collector/browser changes are deployed and the installer is published as npm `openmerit@0.1.9` (`latest`). Activation requires an install command with applied configuration and connected verification, correlated by permitted setup and installation UUIDs; status/doctor checks cannot activate an installation. First observed invocation/task and repeat-use charts derive from that stream, not fabricated first-use events. ## Runtime boundaries

`scout/pipeline.mjs` refreshes structured feeds, schedules incremental Parallel research, validates cited records through Decisions, prepares benchmark/specialist semantics and builds the serving index. `records.mjs` maintains separate entities and observations. `registry.json` holds semantic definitions and operational policy. Research can propose distinct child capabilities; Decisions checks redundancy and parentage before admission. `store.mjs` stages immutable source records, an indexed D1 serving projection, versioned benchmark vectors and specialist groups. The publication Durable Object coordinates hourly writers only. A version check prevents an older run from replacing a newer publication. Requests read the published manifest, apply exact D1 restrictions, load eligible model observations and retrieve prepared specialist/evidence data. Global counts remain catalogue-wide; `retrieval` describes the considered verified catalogue. Specialist reads run concurrently with benchmark retrieval. Manifest polling reuses the immutable manifest until its publication pointer changes.

The initial research policy allows 24 jobs per run, refresh concurrency six, seven-day subject rechecks and 64 relevant specialist profiles. Model selection has no pre-frontier top-K cap; evidence ANN retrieval is supplemented by prepared capability memberships. These limits are operational settings, not model/benchmark-name rules. Discovery is incremental rather than exhaustive. A scheduled trigger is not a promise to revisit every source on every run. Existing structured feeds retain their adapters and exact source aliases; Scout adds research-backed records without requiring another parser for each discovered benchmark.
