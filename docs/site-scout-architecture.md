## Incremental Vectorize writes — deployed 2 November 2026; prune fix not yet deployed

**Receipt.** The owner approved committing, pushing and deploying serving, then the publisher, with a manual run. Commit [45738f6](https://github.com/laz-aslam/openmerit/commit/45738f63bec314a0b75ba5de6c67c6df3fbbf75d) is on `origin/main`; CI passed after a rerun of the `connect-browser` UUID flake. Serving `openmerit-scout-alpha` is version `23df843c` (receipt `.deploys/scout-serving/2026-11-02T18-41-32.644Z.json`, rollback to `e8413821`); publisher `openmerit-scout` is `adcca729` (rollback to `a30bbfc3`). Manual run `manual-20261102-vectors-1` completed with no failed steps and published `81135aa3`: evidence in namespace `evidence` (371 vectors, all new this once), agent catalogue in `agent` (1,617 vectors listed, 45 texts embedded). `validate-and-stage` waited four attempts for the first shared upsert. `/`, `/scout/`, `/connect/` and `/scout/api/status` return 200.

**Pruning failed, fix not yet deployed.** No vector was deleted: the index went from 29,388 to 31,376, exactly the new vectors, and D1 still lists 91 evidence versions and 8 agent versions. Both prunes sent 500 IDs per `deleteByIds` call, and Vectorize accepts at most 20 per call (as `verifyEvidenceReady` already batches `getByIds`); each prune threw, was caught, and kept its references. The agent prune had the same batch size before this change, so it has likely never deleted a vector. Both now delete in batches of 20, six at a time; the first publication after deployment should delete about 13,300 evidence vectors of 84 old versions, and the agent namespaces of versions that age out.

**Finding.** Each publication wrote a full copy of its vectors into a namespace of its own: 371 evidence vectors in `<version>` (never deleted) and 1,612 agent-catalogue vectors in `agent-<version>` (the newest five kept). Embeddings were already cached in R2 by content hash, so OpenAI was called only for changed texts, but on 1 November the index held 25,424 vectors, mostly identical copies, and every publication had to wait for about 2,000 upserts to be indexed before `validate-and-stage` could pass.

**Change.** Both kinds of vector now live in one shared namespace each, `evidence` and `agent`, with IDs that hash the document and its embedded text and no version. D1 lists the vectors each version uses (`scout_evidence_vectors`, `scout_agent_vectors`). Staging upserts only IDs no listed version has, so a publication whose texts are unchanged upserts nothing and has nothing to wait for. Serving filters matches to the active version's vectors: evidence search by the manifest's `evidenceIndex.documents[].vectorId`, agent search by `scout_agent_vectors`. A vector is deleted once no retained version lists it; evidence keeps the newest five versions plus the staged and published ones, as the agent catalogue already did. On the first publication the publisher records the 90 earlier `serving-evidence/*.json` indexes (62 MB) as versions in their own namespaces, so their copies are pruned the same way; earlier agent versions keep `agent-<version>` and are pruned by those IDs as they age out. A failed prune or legacy listing never blocks publication.

**Deploy order.** The serving Worker must go first: the previous serving code queries the namespace named after the version, which new publications leave empty. The new serving code still reads earlier versions, which carry no `namespace` and no listed agent vectors.

## Publisher CPU limit raised to 5 minutes (not yet deployed), 1 November 2026

**Finding.** In manual run `manual-20261101-fireworks-1`, validate-and-stage attempt 6 failed with "Worker exceeded CPU time limit." The step itself is not CPU-heavy: the next attempt, in a fresh invocation, used 5.5 s of CPU. Workflows runs consecutive steps and retries in one Worker invocation, and they share its CPU limit, as they share its subrequest budget. The publisher had the default 30 s. Workers analytics (`workersInvocationsAdaptive` for `openmerit-scout`) show the long invocation of nearly every refresh since 29 October ending at 30–32 s of CPU, as `exceededResources` or just under the limit. In this run the first invocation used 32 s over 29 minutes and the second 30 s over 196 s (collect, interpret and validate attempts 1–6). Workflows restarts the instance and replays completed steps, so most cut-offs were silent. One that lands inside a step costs an attempt and its progress, and a step with few retries (interpret-evidence has one) could fail the refresh.

**Change.** `wrangler.scout.jsonc` sets `limits.cpu_ms` to 300000, the Workflows maximum. Only CPU actually used is billed. Each validate-and-stage retry that waits for Vectorize indexing repeats the staging before the readiness check; the incremental writes below make that wait rare.

## Catalogue rebuild race on step timeout — fix deployed, 29 October 2026

**Incident, 29 October 2026.** Manual run `manual-20261029-agentcatalogue-1` (publisher `5434178f`) ran the catalogue sources and the Hugging Face crawl without failures. The first full apply wrote hashes for all 64,572 staged repositories. Then `catalogue-offerings` took longer than its 10-minute step timeout; it took about 3 minutes in earlier runs. Workflows started the retry while the timed-out attempt kept running, and both used the one shared `cat_offering_stage`: the retry cleared the first attempt's rows, the first attempt swapped in the 8,683 rows then staged and cleared the stage, and the retry also timed out. Live `cat_offerings` was left with 8,683 of 165,330 routes. The run was terminated during the MTEB steps, before publish, so the published snapshot (`54f6839a`, from the 12:07 refresh) and production search were unaffected, and the agent stayed on chat-only data.

**Fix.** `rebuildOfferings` and `rebuildModels` stage rows under a per-attempt token (`run`, starting with the time) and swap in only their own rows, after checking that the staged count equals the rows they built. Rows older than an hour are cleared by the next rebuild. Both steps' timeout is now 30 minutes. A test runs a whole rebuild between another rebuild's staging and its swap.

## Scout agent: every model kind, catalogue search, OpenAI model and result linking — deployed, 29–30 October 2026

**Agent catalogue.** At publication `stageCatalogue` calls `stageAgentCatalogue` (`scout/agent-projection.ts`) after the serving manifest is built. It reads the merged catalogue once (`cat_model_merged`, current base-tier `cat_prices` for non-deprecated `cat_offerings`, `cat_boards`/`cat_board_results`, `cat_mteb_*`). It writes `scout_agent_models`, `scout_agent_boards` and the FTS5 table `scout_agent_search` for the publication ID, then marks `scout_agent_versions.ready`. Scout's chat records stay in `scout_models`. The agent reads both for the active version and never the live `cat_*` tables, so search and shortlist validation agree. Leaderboard ranks are fixed at publication: among all results on a board version, in the board's direction. MTEB uses its published rank. Documents (1,517 on 29 October data) are embedded with `text-embedding-3-small`/256 through the existing R2 embedding cache, so only changed texts reach OpenAI. They are upserted into Vectorize namespace `agent-<version>` of `openmerit-scout-evidence`. The newest five versions besides the one being staged and the published one are kept; older rows and their vectors are deleted. A staging failure is recorded as `agentCatalogue.error` in the manifest and leaves the agent on chat records only. An embedding failure leaves `vectors` null and the agent on BM25. No binding or migration changes. A local replay on 29 October data staged 1,124 models, 103 boards and 1,517 documents in 9–12 s; remote D1 and Vectorize timings are not yet observed. `wrangler d1 export` cannot export the FTS5 virtual table.

**Tools.** `search_catalogue` is new: free-text search over models, benchmarks and leaderboards, hybrid by default (BM25 from FTS5 and Vectorize embeddings merged by reciprocal rank fusion, k=60), with `bm25` or `embedding` as overrides. `search_models` and shortlist eligibility take a `kind` filter. Prices are per unit (token, image, second, character, page, request) and sorted within one unit. `get_model_details` returns leaderboard and MTEB results. `submit_recommendation` accepts any kind, allows fewer than five when fewer are eligible, and computes cost from a unit-aware workload; citations must be the model's own results. For each model it uses the route that prices the most of the kind's main quantities (images for image models, audio seconds for transcription), then the fewest unpriced quantities, then the lowest cost. An image model billed per image token (OpenRouter's GPT Image and Gemini image routes) prices `images × imageOutputTokens` at its `output_image` token rate; without that estimate the images stay unpriced. Real turns on `gpt-6-sol` against a local copy of the 29 October catalogue (Hindi transcription, product photos, multilingual embeddings, a TypeScript coding agent) each took four model requests, 15–18 s and $0.04–0.09, and each shortlist was accepted on the first submission.

**Agent model.** `SCOUT_AGENT_MODEL=openai/<id>` runs the agent on OpenAI's Responses API through pi-ai's OpenAI provider with `OPENAI_API_KEY` (`scout/agent/model.ts`); other values still run on Workers AI. The serving configuration and default are `openai/gpt-6-sol`. On 29 October the serving Worker's `OPENAI_API_KEY` was replaced with the project key (version `74d90b53`, a secret change only), because the previous value most likely belonged to the key that had returned 401.

**Result linking.** `linkResults` (`scout/catalogue-boards.ts`) links a result to one catalogue model by the first of four exact tiers that names anything, and only when it names exactly one model: a reviewed alias (`reviewedAliases` in `scout/catalogue-identities.ts`, 49 entries reviewed on 29 October, scoped by kind and, for generic names, by board); an `owner/name` equal to a catalogue model ID or Hugging Face repository, whatever the model's kind; that name under the same owner; or the exact name of one model of the board's kind. Names normalise versions one way ("Veo 3.0", "Veo v3" and "Veo 3" agree) and drop a trailing ", Maker". There is no substring or fuzzy matching. MTEB results gain a `model_id` column (added by `ALTER TABLE` at the first import) linked by the same rules with kind `embedding`. A read-only live replay moved the 26 stored boards from 501 to 650 linked results of 1,700, and MTEB from no stored links to 1,426 of 12,936 rows (47 models). No existing link changed. MMEB and 3D Arena stay unlinked: the catalogue lists none of MMEB's research models and no 3D models.

**OpenRouter image prices.** `image` and `image_output` are per image token (Gemini image output: 0.00003, $30 per million), not per image; they are now stored as `usd_per_mtok`. Earlier rows stored them as `usd_per_image`, about a million times too low as per-image prices; the next OpenRouter import closes those intervals.

## Hugging Face provider crawl applies only changes — deployed, 29 October 2026

Until now every refresh that followed a completed crawl crawled again and re-applied all of it. Run `manual-20261029-sealfamily-1` spent 09:04–10:20 UTC on the crawl: collecting 130 pages took about 4 minutes, and re-applying 64,575 repositories took about 72, about 1,000 repositories per one-minute step, nearly all of them unchanged.

Collection is unchanged: it still reads the whole feed, because withdrawal needs the complete list of served repositories. Each staged repository now carries a hash of its metadata, leaving out download and like counts. `cat_hf_provider_seen` keeps the hash each repository was last applied with. The apply phase skips a repository whose hash matches and that was applied within `providerReapplyDays` (7). It applies new and changed repositories as before, and withdraws repositories missing from the feed as before. A withdrawn repository's hash is forgotten, so it is applied in full if it returns. The 7-day re-apply carries identity links, parser changes and popularity counts to unchanged repositories. Until then their `last_seen`, downloads and likes are those of the last apply.

The first run after deployment has no stored hashes and applies everything once. After that a refresh should spend minutes on the crawl, with a full re-apply about weekly. Not yet measured on the live feed.

## Answer cache and specificity-first frontier — deployed, 27 October 2026

**Deployment receipt:** the owner approved the commit, push and deployment of both Workers. Commit [848a53a](https://github.com/laz-aslam/openmerit/commit/848a53a) is on `origin/main`. Serving Worker `openmerit-scout-alpha` version `6919c5cf` and publisher `openmerit-scout` version `c1871492` are live (the publisher's first two attempts failed with a Cloudflare 500 on the asset-upload session before uploading anything). Search-time changes apply now; live generation is `18b7d5ed`.

**Why results varied.** A diagnostic run of eight cases, four times each, against generation `9242132d` showed that every repeat produced a different decomposition `search` text, which changed the capability weights, the retrieved benchmarks (mean Jaccard 0.25–0.92) and the accepted tiers. Pinning only the decomposition raised mean top-five overlap from 0.34 to 0.70; the evidence assessment and Decisions answers account for the rest. Two of 32 runs failed with "Task evidence applicability is unavailable": the assessment call allowed 1.8 s with no retry, and observed latencies ran 265–1,383 ms.

**Answer cache** (`scout/answer-cache.ts`). `matchTask` wraps the provider transport. Each Responses, Decisions and embeddings request is looked up in D1 table `scout_answers` by SHA-256 of URL and body; a hit is replayed and marked with `x-scout-answer-replay`, so diagnostics record no provider generation. Misses are recorded and written by `commit()` only after the whole search completed without a degraded assessment or unavailable specialist check. Values are AES-GCM encrypted with a key derived from the same request, so stored rows reveal no prompt text without it. Entries older than seven days are deleted on each write and ignored on read. Because request bodies include the catalogue context, the interpreter version and the `referenceTime` (now day precision), a new generation, version or UTC day misses naturally. Store failures fall back to the provider. Response bodies are read directly rather than through `clone()`: a clone of an aborted response stayed pending and held `commit()` open in the concurrent audit.

**Specificity first** (`pareto.mjs`). Each estimated configuration gets `specificity`: 2 for a fitted direct benchmark or calibration observation, 1 for domain, 0 for general proxies. Within the quality band, the configurations at the highest tier present form their own Pareto frontier and carry the strongest, value and fastest labels; lower-tier configurations follow, ordered within themselves, and cannot dominate the leaders. `rank.mjs` warns about any listed model without the leading tier.

The assessment call now allows one retry (`maxRetries:1`) within up to four seconds.

## Benchmark-row matching through catalogue aliases — deployed, 26 October 2026

Before this change, Scout placed a benchmark row only when its normalized name equalled a Scout model's ID suffix, canonical slug or name, after stripping one effort suffix and one trailing parenthetical, plus nine hand-written aliases. Measured against generation `04c70031f2d10174e21049ef73aedde9` and the 26 October feeds, 911 of 2,113 distinct scored row names (43%) matched.

- **Catalogue aliases.** `loadCatalogue(...).aliases(models)` in `scout/catalogue-routes.ts` maps every name the D1 catalogue knows for a canonical model to the Scout model that owns it. The names come from canonical IDs and names, every listing's provider model ID (without a namespace or `:tag`) and listing name (without a `Lab:` prefix), Hugging Face repositories, Epoch's model records, and linked Hub repositories. ## Refresh memory: smaller documents and ASCII storage — 25 October 2026

The memory failure returned in two steps. 37 of the 50 hourly runs before the twice-daily change failed. `collect-public-feeds` usually failed, and runs that got past it then failed in `interpret-evidence`; a manual run after the first fix below did exactly that. The published records file had grown to 41.4 MB. Research took 19.0 MB of it, across 1,476 records. The 360 benchmarks took 16.5 MB, of which 10.9 MB is per-capability interpretation over the 210 registry capabilities.

Measurement showed that peak memory comes from parsing single large documents, not from holding the parsed data. Parsing one document transiently needs about four to five times its size. The files also contain non-Latin-1 text, so V8 holds each whole document as a two-byte string.

The changes:

- **Research stored separately.** Publication writes research to `catalogues/<id>.research.json` beside the records file, and `store.mjs` `readPublished` loads either part. Collection reads only the records and writes `collected.json` as `{next}` without the previous generation. Research planning reads only research. Evidence interpretation re-reads the published generation, which the refresh lock keeps unchanged until this run publishes.
- **ASCII, piecewise writes.** `putJSON` escapes non-ASCII as `\uXXXX` and serializes large containers piecewise into one byte buffer. Every stored document therefore parses as a one-byte string, and no step builds a whole-document string.
- **Interpretation loads largest first.** It parses the published generation before its own snapshot and releases inputs once `integrateResearch` has copied them. `integrateResearch` no longer deep-clones research records, which it only replaces. The candidate's research goes to `runs/<id>/candidate.research.json`, which staging reads back.

Catalogue content and the publication digest are unchanged, and generations published before the split still load. Escaped JSON parses to identical values, so serving readers are unaffected.

Measured on production generation `e8b5c21256a782acbd45247c34b1fdf9` with recorded feeds replayed and semantic calls stubbed, as the minimum Node heap including R2 byte encoding:

| `collect-public-feeds` | 161 MB | 161 MB | 97 MB |
| `interpret-evidence` (no new research) | 219 MB | 144 MB | 118 MB |
| `collected.json` | 62.0 MB | 18.3 MB | 18.3 MB |

"First run" means reading today's single-file, non-ASCII generation, which happens once; its first publication writes the split ASCII format. ## Runtime boundaries

`scout/pipeline.mjs` refreshes structured feeds, schedules incremental Parallel research, validates cited records through Decisions, prepares benchmark/specialist semantics and builds the serving index. `records.mjs` maintains separate entities and observations. `registry.json` holds semantic definitions and operational policy.
