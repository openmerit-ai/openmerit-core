# Interactive delivery-resolution experiment

This guide describes the separately deployed website experiment, build `guided-20261002-v9`. Its application source is preserved on `codex/main-before-terminal-2026-10-12`; main’s `site/demo/` remains the historical recorded player. The hosted experiment and the terminal’s fictional [before/after sample](https://dash.openmerit.ai/demo) are separate products.

Revision `guided-20261002-v9` of the [interactive demo](/demo/) presents five business scenarios: a delivery policy update, privacy update, an in-house deployment preference, peak-time response needs and an incomplete customer request. The agent has one prepared goal: resolve a damaged delivery before a customer's event. Four sequential model calls read the store policy, assess the affected order and delivery options, choose a resolution, and draft a customer reply. The fourth call is a real model response. No refund, shipment or customer message is executed.

## Run one request

Select **Run request**. John is a member with a $240 order. One $90 desk lamp arrived damaged two days ago; the other items are fine. He needs a replacement before an event in three days. Stock is available, but standard delivery takes five days. Express delivery takes two days and costs the store $12.

The agent must use the affected item's price rather than the order total, apply damage coverage despite the final-sale label, check stock and the delivery deadline, apply the member express allowance, and respect the human-approval limit. Express coverage starts off. John’s standard delivery would miss his event, so the initial correct offer is a $90 item-only refund. Enabling express coverage changes the correct offer to a free two-day replacement, with the store covering the $12 shipping cost. Other prepared cases require an item-only refund, review or a decline.

The starting assignment is Gemini 3.1 Flash Lite through OpenRouter for all four tasks. This is a fixed starting example, not an OpenMerit-selected or approved setup. Each output is checked. It runs once per session; its four calls and cost count toward the session allowance. A passing opening request does not consume a comparison cycle. Since revision v8, a failed business check, response-time check or provider call automatically starts the existing full comparison under the same rules. That recovery consumes one fresh comparison and uses the existing call/spend allowance, preserving verification resources.

The task blocks light up blue as calls run, green for passed checks, and red for failures. A completed passing request shows its proposed resolution and the actual fourth model's **Draft reply · not sent**. A failed opening request remains in the evidence. Since revision v8 the demo immediately compares alternatives and keeps scenario controls locked; it does not ask the visitor to diagnose the failure or relax a business rule. A qualifying result is a proposal, still requiring **Use this setup** and fresh verification. If the bounded search fails, no setup is applied. Drafts and request metrics are hidden during a new run, after a rule change, or when the draft is not valid for the displayed session state.

## Decision instructions and recovery

The resolution prompt separates damage claims from ordinary returns. Damage claims explicitly ignore the final-sale label and ordinary membership window, then apply damage expiry, human approval, stock and on-time shipping in order. The model must return the reason belonging to the selected branch. The application still passes real upstream output to later calls and compares the result against an independent expected outcome; no answer repair or relaxed grading is introduced.

This addresses the observed v7 error where a covered damaged item was declined as final sale, or refunded with an inconsistent `final_sale` reason. Live decision-only canaries test eight cases on each of the starting OpenRouter model and direct OpenAI model, including an undamaged final-sale counterexample; these are separate from whole-agent qualification. Passing one request or one task is not proof that a complete setup qualifies. In the subsequent local v8 browser validation, a mixed setup with three hosted open-weight assignments and a direct OpenAI resolution assignment passed all four comparison cases, both fresh verification cases and John’s rerun. Earlier failed candidates remained in the evidence. This is a small prepared-suite result, not a guarantee for other requests or future runs.

## Explore business scenarios

This revision has five yes/no scenarios under **What changed?**, all off initially. Run the opening request, then select a scenario. Each selection immediately starts reassessment; it does not directly choose a model.

| Scenario | What changes in the experiment |
| --- | --- |
| **We now cover urgent replacements** — Policy update | Members receive express delivery costing the store at most $15 when it can meet their deadline and standard shipping cannot. The policy extraction, expected resolution and reply checks change. John's confirmed damage claim changes from a $90 item-only refund to a free two-day replacement. |
| **Customer data needs tighter protection** — Privacy update | The fictional company allows customer-data tasks only through its approved endpoint, direct OpenAI. Public-policy calls can still use OpenRouter. This is endpoint eligibility, not a claim that a provider guarantees privacy; hosted open weights are subject to the same restriction. The business-facing card does not name or prescribe a model. |
| **We want to run this ourselves later** — In-house option | Prefer compatible reviewed open-weight assignments that pass the complete suite, then measured cost or response time. These calls still use OpenRouter in the cloud. This does not measure local deployment feasibility. |
| **The support queue is filling up** — Peak time | Prioritize the lowest measured worst-case response time, with a five-second limit per complete test instead of twenty seconds. This represents the business need for faster answers; the demo does not generate a traffic burst, measure throughput or establish a production capacity guarantee. |
| **The customer gives us less to go on** — Incomplete request | John's message no longer establishes whether the lamp is damaged, opened or unused. The facts call must return `condition: unknown`, the resolution must be `clarify / missing_context`, and the reply must ask one relevant question without offering a refund or replacement. The displayed customer message changes too. |

The incomplete-request scenario changes both comparison and fresh verification inputs. Other cases still contain explicit damage, so a setup that always asks a question cannot pass. Missing condition takes precedence over a remedy or approval decision: the agent must establish what happened first. Enabling a delivery benefit cannot authorize a replacement when condition is unknown. Inputs supplied to the models never include the hidden expected condition or repaired outputs. Every proposed four-call setup must pass the entire suite; a stronger model is not assigned by name.

There is no scenario-to-model mapping. OpenMerit selects from setups that satisfy endpoint eligibility, business checks and the response limit using measured tradeoffs. A scenario can change the correct customer outcome without requiring a different model. Models that still pass and remain the best measured choice stay in place; no swap is staged for the demo.

Human approval above $150 per affected item remains a fixed store rule in the UI, rather than a scenario toggle. Exactly $150 does not trigger it, and the whole order total is not substituted for the affected item's price. Damage claims retain a 14-day inclusive window and override final-sale labels. A missing receipt requires review once condition is known. Prefer an in-stock replacement that meets the deadline: standard shipping first, then covered member express shipping when enabled. Otherwise offer an item-only refund. There are no sliders or model-picking controls. The backend retains bounded inputs for prepared experiments, including older approval/model restrictions. Older builds require a fresh session.

All five switches and **Reset scenarios** are disabled immediately while a request starts, comparisons run, approval is verified, or John's request is rerun. They visibly dim and explain when they unlock. A lost connection keeps them locked until the session status is recovered. Approval stays near the result, above the scenarios.

Changing delivery policy or customer context requires fresh comparison evidence. Measurements can be reused only for exactly the same business policy and prepared cases in the same build. Privacy changes recheck endpoint eligibility; the deployment preference and response target are reevaluated against applicable measurements. Reuse is labelled in the explanation and trace. The one-case opening request is never substituted for four-case comparison evidence. Changing a scenario pauses the previous setup until approval and verification.

Changed task assignments show the previous and proposed model. **Why this choice?** reports whether the earlier setup failed a task/business check, missed the deadline, or remained a qualifying but less preferred measured tradeoff. An individual step's passing output is not proof that the entire setup qualifies. A comparison with no fitting initial setup automatically starts a broader search under unchanged business rules.

With the in-house preference off, the first comparison tests four complete configurations: OpenRouter AutoRouter, Gemini through OpenRouter, direct OpenAI models, and a mixed assignment. Later policy comparisons include a previously activated expanded assignment in place of the original Gemini starting setup. Other prepared assignments, cached applicable results, new task combinations and catalogue models are available to broader search. Keeping the initial batch to four leaves room for successive business-rule changes within the existing session limits; every fresh batch also reserves verification resources. AutoRouter is an inference option, not an opponent. Its selection is restricted to the disclosed shortlist; served models are retained in the trace and downloaded evidence. No configuration is forced to win.

## Hosted open-weight scenario

**We want to run this ourselves later** uses a reviewed shortlist: [Qwen 3.5 9B](https://huggingface.co/Qwen/Qwen3.5-9B), [Llama 3.1 8B](https://huggingface.co/meta-llama/Llama-3.1-8B-Instruct), [Gemma 3 12B](https://huggingface.co/google/gemma-3-12b-it), and [Mistral Small 3.2 24B](https://huggingface.co/mistralai/Mistral-Small-3.2-24B-Instruct-2506). This is a curated candidate set, not a popularity ranking or a hardware recommendation. The live OpenRouter catalogue must still list each candidate with compatible structured outputs, context size and prices. A release with an announced catalogue expiration is skipped. Unreviewed models are not inferred to have open weights from their vendor name.

Task cards use the shorter **Open weights** badge. A note below the scenarios states that all calls run in the cloud. The read-only inspector, model-call trace and downloaded evidence retain **Open weights · Hosted on OpenRouter** and the actual provider. The demo measures hosted API charges and wall-clock latency. It does not measure local hardware, memory, throughput, deployment feasibility or local data privacy. Hosting on OpenRouter still sends inputs to cloud providers, and endpoint restrictions continue to apply to every private step.

Enabling the scenario tests compatible open-weight assignments first, using permitted direct models on any tasks whose endpoint restrictions exclude OpenRouter. All four business cases and the response-time limit must still pass. A derived `preference_fit` score records the fraction of the four assignments using reviewed open-weight releases; it is metadata-based preference evidence, not a quality or privacy score. The coordinator includes it in the verified frontier. Selection prefers the highest fraction, then the existing cost or live-chat timing priority. A more expensive qualifying open-weight setup can therefore win without inventing a saving.

When the initial candidates fail, broader search can retain successful open-weight tasks and test another model on the weakest task, then use the existing bounded fallback search. Every combination faces the complete suite. A mixed setup or a setup with no open-weight assignments may be proposed when it is the qualifying result found within the allowance; the explanation reports the actual count. If catalogue discovery fails, other permitted options remain available. No switch forces a specific model to pass or relaxes a business check. Turning the preference off restores the usual cost/timing selection and can reuse evidence for unchanged business cases. Approval and fresh verification remain required.

The pool stays bounded at eight catalogue candidates, including compatible reviewed open-weight releases and direct OpenAI candidates. Existing call, spend and verification reservations are unchanged. In the 2 October v7 local live check, all four reviewed families were called successfully, but none of the tested complete or mixed setups passed every default-policy case. The best mixed setups passed three of four cases. No setup was approved; successful dispatch is not evidence of a qualifying agent.

## Automatic broader search

A comparison with no qualifying initial configuration automatically enters **Searching other models**. Search can also investigate a better open-weight fit when an existing qualifying setup uses fewer open-weight tasks than the endpoint rules permit; the UI distinguishes this preference search from a failed business check. The response-time limit, express policy, approval requirement, business fixtures and grading remain unchanged during the search. No additional switch or approval is needed for evaluation within the already authorized session allowance.

The harness reads OpenRouter's model catalogue and the configured OpenAI account's model list. OpenRouter candidates must support this text/structured-output request format, have a sufficient context window and stay within the existing $1 input/$5 output per million token dispatch ceiling with no request fee. Catalogue latency ordering is a research lead, not a measurement of this workflow. Direct OpenAI discovery uses account availability intersected with adapters that have checked request semantics and token rates: GPT-5.4 nano and GPT-4o mini supplement the original GPT-4.1 options. Other OpenAI models are not yet supported by this demo. Catalogue failures are recorded independently; one unavailable source does not hide the other source's candidates.

The bounded pool contains up to eight additional compatible models. Task-level checks and timings can suggest a new combination of previously tried models; untested prepared assignments and newly discovered models can also be tried. Every proposed combination is run through all four comparison cases with real sequential calls. It cannot qualify on estimated latency, catalogue rankings or successful individual steps alone. Each round uses prior task results to suggest a combination, then considers remaining prepared assignments and compatible catalogue models. No assignment is automatically promoted just because it is new.

The search stops at the first qualifying additional setup (or first improvement in open-weight coverage during a preference search), after at most six extra setups per comparison, when its compatible options are tested, or when session/call/spend limits prevent another complete test. Twelve calls and a conservative spend allowance are preserved for approval verification and the original request rerun. The comparison and its expansion count as one fresh comparison. Failed configurations and catalogue sources remain in the evidence download. A failed fresh verification or rerun also disqualifies that assignment on subsequent comparisons wherever the recorded failure still violates the current requirements; earlier passing comparison evidence cannot silently override it. Unchanged workload results can be reused on subsequent rule changes; their current restrictions and time limit are always rechecked.

While search runs, controls stay locked and the read-only IDE and trace follow the new model assignments. If no setup qualifies, the UI identifies the stopping reason and, when available, the fastest correct setup's slowest measured case against the deadline. Earlier task blocks are labelled **Earlier scenario**, not **Passed**. Search exhaustion does not prove that no model outside this bounded search could qualify. The demo never silently relaxes the requirement or applies a failed configuration.

## Read and approve the choice

The compact page shows one customer request and four task blocks. During a comparison, a caption identifies the prepared case currently being tested, so the blocks are not presented as calls for John alone. Amber marks a proposed changed assignment. **Why this choice?** contains the explanation, measurements, other candidate results and session usage. Labels accompany every semantic color.

The UI pairs the demo on the left with a read-only **Behind the scenes** view on the right; the two panels are centered together on desktop and stack on smaller screens. Taller workflows scroll normally. The inspector uses a muted gray surface, softer borders and restrained syntax/status colors so the interactive panel remains the focus. Text, live highlights and errors remain readable. One code view shows the current constraints, prepared steps, model assignments and checks. The active call is highlighted and brought into view automatically. Changed rules and proposed model assignments are marked in amber. These are views of configuration and session data, not editable source files. The run trace stays visible underneath as a compact monospace console, with timestamps, source labels and colored RUN/OK/WARN/ERROR/INFO markers. The original event messages remain intact. All actions, including **Download run evidence** under **Why this choice?**, remain on the left. The right side has no tabs, buttons or editing controls and starts no model calls.

The view distinguishes the starting assignment, a proposal awaiting approval, verification in progress, and a verified setup. Earlier rules, stopped sessions and lost connections are labelled explicitly. A comparison can run two setups concurrently; the code follows the latest reported task while the trace retains events from both. Returned output is shown only when the displayed request has completed and the rules still match. Scrolling back preserves the reader’s position; a new action on the left resumes automatic code following. The trace follows new events while the reader is at its bottom.

Each configuration faces four synthetic cases: John's event deadline, an out-of-stock item requiring a refund, a high-value item that tests the approval switch, and a missing receipt with instructions to falsely claim the entire order was refunded. Two routes may run concurrently; calls and cases within each route are sequential. Policy, extracted facts, resolution and reply commitment fields are checked exactly against independent expected values under the current rules. The draft also receives bounded wording checks for required outcome wording, amounts and common false action claims. These checks do not constitute a full semantic evaluation of its prose.

An upstream mistake is retained and passed to subsequent calls; it is not repaired with an expected answer. The application supplies arithmetic comparisons calculated from the actual extracted policy and facts, including delivery timing and express coverage. The third model applies rule precedence and chooses the resolution; the fourth model receives that actual resolution and writes the draft. These helpers and inventory/delivery snapshots are prepared application code and fictional inputs, not live commerce integrations.

The prepared harness calculates the comparison; the actual OpenMerit coordinator validates the typed evidence and frontier and records its lifecycle. Model and harness activity are labelled separately from OpenMerit events. This demo does not run Pi as an autonomous investigator, invent integrations, or exhaustively search all model assignments. Its broader search uses the bounded strategy described above.

The frontier compares task success, observed maximum whole-request time and API cost on the same cases. Local v7 also includes derived open-weight preference fit when that scenario is enabled. After the enabled open-weight preference is applied, live chat recommends the lowest observed maximum time; otherwise it recommends the lowest measured API cost within the time limit. Ties use the other metric, then a stable configuration ID. The core validates the frontier and the evidence-backed preference; the prepared harness calculates the recommendation. Reported average latency is separate. Business rules can increase cost or latency, and no saving is guaranteed. **Use this setup** records the exact approval, applies the selected configuration, and makes fresh calls on two separate boundary cases: exactly day 14, exactly the review threshold and exactly $15 express cost; and expired damage coverage on day 15. Every completed case makes four calls. The guided flow then reruns John’s original damaged-delivery request with fresh calls. It does not display a verification fixture as John’s request. The core’s reference is a measured candidate within the comparison; the separate one-case opening example is not treated as that four-case baseline. If the comparison reference remains best, the core records its use and fresh checks without claiming a core model-swap transition. Failed verification stops the application; it does not restore a setup that may violate new requirements.

**Run John’s request again**, under the explanation, reruns the same known fictional case with fresh model calls. It is not an unseen validation set. Changing a requirement disables this action until reassessment. A failed live example pauses further work.

## Measurements and data

Times are observed wall-clock durations, including all four sequential calls and small harness overhead. The suite is too small to estimate production reliability or latency distributions. The requirement uses the observed maximum, not a promised service level.

OpenRouter cost is the provider-reported charge. Direct OpenAI cost is an estimate calculated from actual input, cached-input, and output token counts using checked published rates for each supported direct model (GPT-4.1 mini/nano, GPT-4o mini and GPT-5.4 nano). It is not an invoice. The cost and latency cards beneath the result cover John’s displayed request, labelled as a comparison case when proposed. Values stay neutral because a rule change may increase or decrease either metric. They appear after a completed measurement and are hidden while a run is in progress or the rules have changed. Expanded comparison measurements report the four-case average and maximum separately. Changes in John’s request cost and time are shown under the explanation; different business rules can increase or decrease either. The session ledger also includes the opening request, other candidates, verification and live examples. Container infrastructure and engineering are excluded. Missing cost evidence is not treated as zero.

All requests are constructed from fictional fixtures. The browser never receives API keys or container authorization tokens. Model output, synthetic inputs, measurements, and an event trace are available through **Download run**. The full experiment and core audit artifacts are also written inside the temporary container. The demo is cloud-only; it does not claim local inference or measure local hardware.

## Session limits

A session lasts up to 30 minutes and permits at most three fresh comparisons, 12 comparison/review cycles, 240 model calls, and $2 of conservative inference reservations. There are at most two concurrent sessions and 12 admitted sessions per UTC day shared across the site. There is no separate three-session limit for people on the same network. A session that closes or expires without reserving any model calls returns its admission slot; this also applies when a container fails to start or starts with an outdated runtime. Startup attempts remain limited to 36 per UTC day. Once a model call is reserved, that session counts toward the daily allowance even if the call fails. Reservations are retained conservatively. Temporary API keys and service availability can make live inference unavailable.

If the shared allowance is exhausted, new sessions open at 00:00 UTC (4 a.m. Dubai). Existing unexpired sessions can continue within their own limits.

If the connection drops while starting, the page checks whether a session was created. If none exists, **Run request** becomes available again; no model call is implied by a startup or reconnecting message. Expired sessions and sessions from an earlier demo version offer **Start a new session**. Completed evidence belongs to its original session.

**End session** closes admission and destroys the container. A session cannot resume its live work after a process restart. It keeps its stopped status rather than presenting stale approval as active. These limits and the small prepared suite make this an experiment, not production readiness evidence. The earlier recorded demo and its guides remain archived.
