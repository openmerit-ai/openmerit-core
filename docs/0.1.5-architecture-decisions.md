# OpenMerit 0.1.5 architecture decisions

Status: implemented for collaborator review
Date: 2026-09-17

## Context

OpenMerit is intended to become the open, vendor-neutral
**best-model-for-this-task-at-this-moment layer**. It works with harnesses,
providers, and observability systems, but it must not become any of those
products itself.

The 0.1.4 repository contained two overlapping products:

1. A session-bound decision loop triggered by the Pi extension.
2. An older daemon that crawled Pi traces, watched an OpenRouter catalog,
   queued new models, ran shadow trials, and emitted unbound recommendations.

The first path expressed the product boundary. The second path blurred it,
duplicated lifecycle ownership, was partially disconnected, and made the
runtime appear to be a harness, provider client, and observability crawler.

0.1.5 makes the session-bound decision loop the only shipped runtime path.

## Decision 1: OpenMerit is a decision control plane

OpenMerit accepts normalized task outcomes and eligible model routes from a
harness integration. It returns evidence and a policy-gated route decision.

Normal application traffic remains between the harness and provider. OpenMerit
does not intercept it. Local JSONL is retained as an auditable default evidence
store, not as an attempt to become an observability platform.

Why:

- The product's authority is route selection, not task execution or telemetry
  collection.
- Integrations can change without changing decision semantics.
- The party operating the product keeps control over credentials, eligible
  routes, privacy boundaries, and policy.

## Decision 2: remove the daemon and trace crawler

Removed runtime behavior:

- Recursive Pi session-directory crawling.
- Incremental trace cursors and derived observation logs.
- The `openmerit watch` command.
- The new-model queue and background shadow-trial loop.
- Historical, session-unbound `openmerit recommend` generation.

Why:

- Harnesses know when a task is complete and can provide an exact normalized
  outcome; crawling their storage is less reliable and couples OpenMerit to an
  observability format.
- The previous incremental reader did not preserve a partial task across poll
  boundaries, so a user message and assistant result arriving in different
  ticks could be separated.
- `trialTick` existed but was not called by either daemon entry point, leaving
  queued catalog models unconsumed.
- Session-bound evidence is safer for automatic decisions because task,
  baseline route, and application target can all be revalidated.

Future observability products should integrate through a normalized outcome or
evidence interface. OpenMerit should not ingest every vendor's storage format
inside its decision kernel.

## Decision 3: remove direct provider ownership

Removed runtime behavior:

- Direct OpenRouter, OpenAI, and Gemini evaluator clients.
- OpenMerit-owned provider credential loading.
- Dynamic OpenRouter provider registration inside Pi.
- Catalog-driven injection of models not configured in the harness.

The Pi integration now runs evaluator calls through Pi's route registry and
credential store. Other harnesses can implement the same inference contract.

Why:

- OpenMerit is not a provider, reseller, or gateway.
- A route must be explicitly eligible in the active harness before OpenMerit
  can spend money on or switch to it.
- End-to-end provider neutrality requires preserving the exact selected route,
  not silently moving a logical model through OpenRouter.
- OpenMerit should never require a privileged universal provider credential to
  perform its core decision job.

External catalogs remain valuable for discovery, availability, deprecation,
and price signals. They should return normalized signals through optional
connectors in a future release; they should not execute inference or mutate a
harness's provider registry.

## Decision 4: remove the public standalone trial harness

Removed:

- The `openmerit trial` command.
- The standalone trial orchestrator and task JSON example.

Why:

- Shipping a separate task runner makes OpenMerit look like a harness.
- It duplicated selection, evaluation, budgeting, and recommendation logic.
- Controlled benchmark runners already exist under `benchmark/` for developer
  validation.

Candidate execution remains behind `HarnessAdapter`. Pi is the first adapter,
not a permanent core dependency.

## Decision 5: benchmarks stay in the repository, not the runtime

The invoice, text-to-SQL, and policy-adjudication benchmarks remain checked in
and continue to be replayed by `npm run benchmark:verify-recorded`.

Removed from the runtime:

- Invoice-specific scoring and prompting.
- Packaged invoice images and ground truth.
- Hard-coded task keyword classification and benchmark-name routing.
- Live OpenRouter/Artificial Analysis shortlist logic.

Why:

- A universal decision layer cannot contain special cases for one benchmark.
- Public benchmarks are possible cold-start priors, not proof of value on a
  user's actual workload.
- Keeping benchmark data out of the npm artifact reduces package size and
  separates regression evidence from production behavior.

Future priors should be optional normalized signals with source, timestamp,
scope, and confidence.

## Decision 6: candidate selection is deterministic

The LLM strategist and its hard-coded preferred models were removed. 0.1.5
selects an auditable price-spread slate from policy-eligible harness routes.

Why:

- Critical routing infrastructure must be reproducible and explainable.
- An LLM choosing which competitors receive trials adds cost, instability, and
  model-family bias before any task evidence exists.
- Hard-coded preferred model names age immediately and compromise neutrality.

The deterministic selector is deliberately small. It is a stable base for a
future exploration policy using task history, uncertainty, capacity,
reliability, and external priors.

## Decision 7: keep evaluation, but make it an integration

OpenMerit still needs a default way to convert task outcomes into comparable
quality evidence. The evaluator therefore remains, but:

- It executes through a harness-owned exact route.
- `evaluator_model` is configurable.
- No provider or model is hard-coded as preferred.
- Scores are validated and clamped to the documented 0..1 range.
- Visual evaluation is generic rather than invoice-specific.

One evaluator score is not treated as ground truth. Repeated evaluation,
deterministic task validators, real user outcomes, and calibrated uncertainty
are expected future evidence sources.

## Decision 8: preserve the evidence and policy kernel

Retained:

- Stable logical model identity plus exact execution route identity.
- Quality, price, and latency Pareto frontiers.
- Session-bound recommendations with gate reasons.
- A measured current-route baseline requirement.
- Provider allow/deny rules and exact-route metadata overrides.
- Primary and fallback selection.
- Append-only recommendation and trial history.
- Atomic snapshots and malformed-JSONL recovery.
- Candidate workspace isolation and default no-tools execution.
- Provider-extension allowlisting for custom Pi routes.

Why:

These pieces express OpenMerit's actual product: evidence-driven route
decisions under user-owned constraints.

## Decision 9: harden budgets and automatic application

Changes:

- Ledger updates now use a process lock to prevent lost read-modify-write
  updates across simultaneous Pi sessions.
- Per-trial admission includes task text, image bytes, attached-file sizes, and
  a bounded output estimate.
- Policy numbers and booleans are validated instead of accepting negative,
  fractional, or truthy malformed values.
- Before automatic application, the extension rechecks the recommendation
  against the current policy as well as the current task, session, and route.
- Automatic error fallback requires an exact, priced route that still passes
  the current provider and price policy; manual fallback remains available.
- `fallback.auto_update` now controls whether an applied recommendation updates
  the stored fallback.

Why:

A recorded automatic decision must not remain authorized after the user changes
their policy. Budget evidence must also survive concurrent sessions without
silent lost updates.

The admission estimate is still not a provider-side hard limit. Stronger
reservation and reconciliation semantics remain future work.

## Decision 10: preserve 0.1.x evidence, not obsolete execution paths

0.1.5 continues to read existing trials, recommendations, routes, and status
records. The policy loader normalizes:

- `watch.models_per_task` to `comparison.max_routes`.
- `judge_model` to `evaluator_model`.

Old catalog, observation, cursor, and watcher files are left untouched on disk
but are no longer read or written. OpenMerit does not destructively delete user
state during upgrade.

## Resulting 0.1.5 runtime

```text
Pi extension
  → settled task + exact eligible routes
  → session comparison engine
  → harness adapter executes candidate routes
  → inference adapter evaluates outcomes
  → Pareto evidence + primary/fallback recommendation
  → current policy gate
  → supervised or automatic route application
  → append-only audit history
```

This is intentionally narrower than the full OpenMerit vision. It establishes
the correct authority and integration boundaries before adding live health,
deprecation, capacity, price-drift, outcome, and multi-provider discovery
signals.
