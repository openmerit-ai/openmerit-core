# Scout by OpenMerit

Describe what you need a model to do. Scout returns up to five model-and-endpoint candidates per task. Comparable measurements support performance ranking; narrow decision and vision tasks use an explicitly labelled task-fit shortlist when quality is unmeasured. The `/scout/` page, JSON API, and MCP tool all use the same index and ranking.

Scout is a separate beta product. It does not change the OpenMerit npm package, Pi coordinator, or Inference Terminal. Recommendations are evidence-based candidates for your own evaluation, not a guarantee of task accuracy or an independently validated state-of-the-art ranking.

The proposed beta default records submitted prompts alongside recommendations for matching evaluation and debugging, not foundation-model training. It requires `SCOUT_BETA_EVALUATION_LOGGING=true`, the existing `POSTHOG_CAPTURE_CONTENT=true` and complete account-sync/deletion configuration. The new rollout flag is **not set in production configuration**. Before activation, review the applicable privacy basis, restrict PostHog access, publish the [beta data policy](scout-data-policy.md), and verify the project's AI content storage. This section supersedes the dated default-off contract below only after activation; a beta label does not establish consent or another lawful basis.

With the rollout enabled, browser prompt sharing defaults on only when no saved content choice exists. Existing refusals, general analytics opt-out, DNT and GPC still win; unreadable preference storage keeps content off. The notice beside the prompt reflects the actual setting before submission. Footer controls can disable usage or prompt sharing. No draft text is collected. API/MCP content remains explicit opt-in through `X-Scout-Analytics-Content: on`; `off` or omission excludes it. CLI planning continues to send `off`.

In analytics version 4, the bounded, redacted prompt and up to three task excerpts/five-layer breakdowns exist **only** in `$ai_trace.$ai_input_state`, as `{prompt, tasks}`. The ordered recommendations appear in `$ai_output_state` and the existing content-free `scout_search_details` records. Public evidence, ranks, metric bases, quality-screen status, timings and interpreter/ranker/index versions remain available; they describe recommendations, not model executions. [PostHog Cloud documents 30-day retention](https://posthog.com/docs/ai-observability/data-retention) for these AI input/output fields in `posthog.ai_events`, stripped from ordinary events at ingestion. Ordinary metadata follows normal project retention. No second prompt copy, custom expiry job or batch export is added. Live project expiry is not yet verified; old version-3 detail events and external exports are not retroactively erased by this change.

**Don't link this browser's activity to my account** sends `X-Scout-Analytics-Account: off`. The server substitutes fresh identifiers and excludes account identity/merging, ignoring old browser identifiers and client-supplied trace IDs that might already be linked. This setting applies to future requests from this browser, not other devices or copied coding-agent configuration; API/MCP callers can send the same header themselves. General account opt-out/deletion gates still apply. Separate Clerk profile and lifecycle analytics can continue while usage analytics is enabled. Unlinking does not erase old associations, make identifying prompt text anonymous, or enable automatic account-based deletion of unlinked historical events. Cross-request funnels and returning-user analysis are unavailable for unlinked activity.

## Product analytics

**Release boundary, 22 October 2026:** hosted Scout uses the [unified PostHog integration](#unified-product-and-search-analytics-deployed-22-october-2026) below. New Cloudflare Analytics Engine search writes have stopped; historical records are unchanged. Main-site/docs instrumentation and npm publication remain pending.

Hosted Scout has PostHog product analytics enabled in the EU region. Other deployments remain **inactive without a PostHog project token, region and environment**. The latest rollout confirmed anonymous visits and rejected requests in PostHog storage, with three suppressed validation identities absent. Authenticated searches, profile synchronization and real Clerk lifecycle deliveries still require live acceptance; passing local tests or HTTP acknowledgements do not establish those outcomes. CLI telemetry remains source-checkout-only and has not been published to npm.

The operator's PostHog dashboard has eight charts covering visits, the sign-in journey, recommendation attempts and outcomes, successful-search p50/p95 latency, model-result interactions, API/MCP request outcomes and opt-in CLI completions. Charts exclude test/development environments; early production activity includes rollout checks. Complete authenticated-session tracking, successful searches and result interactions still await real-usage verification and are labelled accordingly. Empty pending charts are not verified zero usage. Reusable metric definitions are saved as unapproved proposals, not canonical metrics. The separate main-site documentation deployment is unchanged.

When configured, explicit events cover visits, opening sign-in, authenticated sessions, rendered results, opening model evidence, successful model-ID copies, provider-link clicks, and bounded failure codes. Interaction events contain task position and model rank, **not the copied ID, link URL or task text**. `scout_search_completed` is server-owned: one event per accepted recommendation attempt, including cache hits and concurrent callers sharing computation, regardless of the number of tasks. It records outcome, task/candidate counts, server duration and cache status. `scout_request_completed` separately measures API/MCP requests, including authentication/validation failures and MCP tool failures returned with HTTP 200. Do not add request, rendered-result and search events together to count searches. A successful recommendation is not evidence of successful model execution.

Authenticated events use a namespaced SHA-256 pseudonym of the **verified** Clerk user ID. The configured profile sync below can associate that identity with a name and verified email after an eligible visit; it is not anonymous data. Raw Clerk user/session IDs, bearer tokens and cookies are never forwarded to PostHog. The same verified account has the same pseudonym across web/API/MCP. `client` (`web`, `cli`, `agent`, `unknown`) is an allowlisted caller hint; `transport` (`http`, `mcp`) comes from the actual route. Neither is an authorization signal. Browser events are client-reported, not a security audit.

The browser keeps a random anonymous ID and hashed account/session transition markers in this tab's `sessionStorage` so an OAuth return can join the visit-to-sign-in funnel. Sign-out/account changes rotate that anonymous ID. With storage disabled, these values remain in memory and redirect attribution may be lost. Anonymous users are not linked across separate tabs or visits; returning authenticated users can support account-level retention. CLI telemetry is separately [opt-in](inference-terminal.md#optional-cli-product-analytics-source-checkout-only), with a process-only identity and no account linking unless a future client actually authenticates that account.

There is no PostHog browser SDK, autocapture, session replay, DOM/text collection, feature-flag polling, geography lookup or IP forwarding. Browser events pass a typed allowlist at `/scout/api/analytics` before the server sends them to PostHog. Server search diagnostics can include bounded public source URLs and separately opted-in, best-effort-redacted prompt text as described below. Explicit exception handlers send sanitized categories and application frames, not raw messages or arbitrary stacks. Disabling analytics does not disable necessary provider processing or erase historical records.

Browser Do Not Track and Global Privacy Control suppress both browser and server-side PostHog events. To opt out for this browser independently, run `localStorage.setItem('scout-analytics-opt-out', '1')` on Scout and reload; remove that item and reload to restore collection. API/MCP clients can send `X-Scout-Analytics: off`, `DNT: 1` or `Sec-GPC: 1`. The event endpoint has a separate per-IP quota, so analytics clicks do not consume the search allowance. Delivery is best effort, without retries; the Worker uses background delivery with a 1.5-second timeout, and an outage cannot block recommendations. Receipt does not prove ingestion. PostHog retention, access, spend caps and any required consent are project/operator responsibilities; Cloudflare's three-month retention does not apply to PostHog.

### Coding-agent activation funnel — source only, not deployed

The setup section adds an optional coding-agent selector. New explicit events distinguish opening setup (`scout_agent_setup_opened`, with button/navigation/disclosure/deep-link source), choosing an agent (`scout_agent_selected`), copying an MCP URL or API request (`scout_agent_setup_copied`, including clipboard success/failure), and opening the API guide (`scout_agent_docs_opened`). Repeated button activations count as interactions; hash changes and native disclosure toggles caused by the same activation do not add duplicate events. These are best-effort browser events, not installation receipts.

**New picker flow — source only:** choosing an agent in the button's picker copies setup instructions and emits the same copy event with `artifact=setup_prompt`. Only a resolved clipboard write has `outcome=ok`; blocked clipboard access records `error` and offers selectable instructions, without claiming a manual copy occurred. No instruction text, user draft or token is sent in these events. MCP activation funnels must include successful `setup_prompt` copies alongside `mcp_url`; existing saved charts filtered to `mcp_url` alone need that update when this UI is released. API-copy funnels remain separate.

Copied URLs carry a public `agent` category: `claude-code`, `cursor`, `codex`, `amp`, `opencode`, `t3-code`, or `other`. Unselected/invalid values become `unknown`. API/MCP callers may instead send `X-Scout-Agent`; the header takes precedence. Copied URLs contain no account, anonymous ID or token. Setup events add only categories, never the copied configuration, URL or raw client name; existing pseudonymous identity properties still apply. MCP is stateless, so clients must preserve the URL query or send the header on every request. Agent attribution is self-reported, not proof of which application ran it. Choosing a brand does not certify client compatibility.

The server emits `scout_agent_connected` only after an authenticated successful MCP `initialize` response. Its optional client-reported name is reduced to the same fixed categories as `reported_agent`; other names become `unknown`. Discovery, ping, copies, authentication failures and tool calls cannot emit this milestone. Request outcomes include the allowlisted `mcp_method`; search and request events retain the selected `agent`, even across cached/shared computation. Browser and agent events join through the verified account pseudonym, not their separate tab/request session IDs.

**Activation means the first observed successful agent search returning at least one candidate**, not local installation or successful execution of a recommended model. Build the ordered funnel from agent selection → successful MCP URL copy → connection → `scout_search_completed` with `outcome=ok`, `candidate_count>0` and `transport=mcp`, holding `agent` constant across those steps. Use seven days as the conversion window and a separate copy-to-success funnel for JSON API use, which has no MCP handshake. An overall opening → copy → connection → successful-search funnel includes users who skip the selector; keep it unsegmented and use the per-agent funnel for constant-agent attribution. Repeat use comes from subsequent successful searches; no browser-local “first ever” flag or new persistent identity is introduced. First observed use depends on retention, consent and identity linking; it is not guaranteed lifetime-first use. Missing events cannot be backfilled.

When usage analytics is off, generated URLs omit the agent category and include `analytics=off`; the server honors this query opt-out as well as privacy headers and account preferences. Previously copied URLs do not change when the browser preference changes, and a copied opt-out URL stays opted out until edited or recopied. API examples explicitly disable prompt-content capture. This instrumentation has not been deployed, and production conversion counts require live acceptance after deployment.

### Unified product and search analytics — deployed, 22 October 2026

Hosted Scout now sends new search diagnostics to **PostHog only**, through the existing first-party ingestion boundary. It stops new Cloudflare Analytics Engine search writes; historical Cloudflare records are neither exported nor deleted. OpenAI processing, the short-lived result cache, catalogue storage and infrastructure logs are separate from analytics and unchanged. Anonymous event ingestion is confirmed; authenticated recommendation traces and errors have local contract coverage but still require live acceptance.

One `scout_search_completed` still counts one recommendation attempt, including cache hits/shared callers. A `$ai_trace` describes that request and `scout_search_details` records each task/slot's ordered shortlist, public evidence, metric bases, quality-screen status and diagnostic context. The server creates a unique `trace_id`, returns it as `X-Scout-Trace-Id`, and the browser includes it on result views/copies/provider clicks. Identities and traces never enter shared computations or cached results. These are **recommendation traces**, not model executions: candidate costs/latencies are reference estimates, not actual LLM charges or task-success measurements. Missing measurements remain null. Evidence is bounded to 20 items per list, depth 10 and a 48,000-character string budget per task/slot; `evidence_truncated` and original benchmark counts disclose omissions while all five compact ranks/metrics remain. Prompt-derived semantic-match prose is excluded.

**Prompt text is off by default.** Under **Privacy & analytics**, visitors can disable usage/account analytics or separately opt into sharing prompts and five-layer task breakdowns. Content needs both the deployment's `POSTHOG_CAPTURE_CONTENT=true` and request header `X-Scout-Analytics-Content: on`; the server also requires complete account-sync/deletion configuration. API/MCP clients can use that same header explicitly; omitting it or sending `off` excludes text. CLI planning always sends `off`. General analytics opt-out, DNT or GPC overrides content sharing. Standard analytics and browser preference changes do not send input text; content is processed only when a task is submitted.

Opted-in text receives best-effort removal of common credentials, authorization values, private keys, emails, IP/phone patterns, URLs and local home/temp paths. This cannot recognize every personal name, proprietary passage or secret. Never submit confidential records. Prompt text is limited to 4,000 characters; layer/excerpt text to 1,000 each. Content is linked to the verified account and is identifiable when profile sync is active. Turning sharing off stops future capture, not in-flight work or historical retention. Profile deletion also requests deletion of these account-linked events. Set suitable PostHog retention, access controls and spending limits before activation; no automatic retention setting or old-data backfill is included.

Browser and server failures produce PostHog `$exception` events. Scout errors contain fixed categories, allowlisted exception classes, and up to 20 application-filename/line/column frames; messages, function names, absolute paths, source context, query strings, headers and arbitrary stacks are excluded. Browser exceptions are capped at three per page. Terminal/CLI and main-site errors currently carry categories/classes without frames. Deployment metadata labels serving releases. No session replay, DOM/text autocapture, fingerprinting or Sentry is added.

Source-only homepage/docs events cover page categories and explicit navigation destinations, with a separate anonymous tab ID and no Clerk linking; that separate site deployment is pending. Opt-in local terminal events cover navigation/map interactions, inspector kinds, bounded aggregate inventory counts and errors, never local model/agent/project names or source content. The same process-only ID links terminal events to its CLI launch. Authenticated Scout web/API/MCP events share the verified account pseudonym, but anonymous website/CLI identities are not automatically resolved to that account. See [terminal telemetry](inference-terminal.md#optional-cli-product-analytics-source-checkout-only). The existing production dashboard has not been updated for this release; new charts, retention changes and historical backfill are not included.

### Account profile synchronization — deployed, 22 October 2026

Clerk-to-PostHog synchronization is **deployed and configured, but not yet verified against real Clerk deliveries**. Its signing secret, account-state binding and project-restricted PostHog person-deletion credential are installed. Without those prerequisites, personal profile export stays off. Clerk remains the identity system; Cloudflare coordinates synchronization, rather than providing a second login provider. There is no Clerk Billing integration. Account deletion is covered locally, not proven against a production account.

After Scout receives an authenticated browser's enabled analytics preference, PostHog receives only the account's **name, verified primary email, signup time and connected Google/GitHub providers**. Values come from Clerk's current Backend API record, not browser-supplied profile data or an old webhook payload. Removed/unverified primary emails and cleared names are removed from the current PostHog profile. Existing accounts synchronize on their next eligible visit; there is no whole-directory backfill. Profiles and behavior use the same account pseudonym, so they are identifiable personal data. Neither profiles nor account IDs are added to the Cloudflare prompt archive.

Verified `user.created`, `session.created` and `session.ended` deliveries produce `scout_signed_up`, `scout_signed_in` and `scout_signed_out`. Session removal and revocation have separate events. Browser session observations become `scout_session_observed`, which links the anonymous visit to the authenticated account but is not a new login. Before this change, `scout_signed_in` meant a browser session observation; dashboards must distinguish the release boundary and must not add the two events together. Lifecycle events use the Clerk event time and stable delivery IDs. Provider attribution is `unknown` for webhook lifecycle events. The browser reports Google/GitHub on session observations only when a completed, verified sign-in attempt identifies that exact session; connected providers and the client's latest sign-in strategy are not proof. Signup or restored sessions can remain unknown.

The signed-in browser sends an authenticated boolean preference to `/scout/api/analytics/preference`, including when DNT, GPC or local opt-out is active. This privacy-control request contains no product event, anonymous ID or profile. Once received, an opt-out stops account-linked events and background profile/lifecycle forwarding and discards unsent lifecycle events. A later enabled preference from an authenticated browser can resume collection for that account; preferences are account-wide and the latest server-observed preference wins. Opt-out is not historical erasure. A browser that is offline, blocked or not signed in cannot update server-held preferences until it reconnects and authenticates. Request-local opt-outs still suppress that request immediately. These controls do not implement a consent banner or establish legal consent.

Per-account Cloudflare Durable Objects hold preference state, hashed profile fingerprints, up to 256 recent delivery receipts and deletion tombstones. Before a preference is known, at most 128 pseudonymous lifecycle events wait up to seven days for an eligible visit; alarms expire the pending buffer. No names, emails, raw Clerk IDs, tokens, webhook bodies or prompts are stored there. Signed webhooks retry through Clerk/Svix on delivery failure; failed preference initialization retries on a later visit. Ordinary product-event delivery remains best effort. Search never waits for Clerk profile retrieval or PostHog.

Deleting a Clerk account stores a permanent pseudonymous tombstone and requests deletion of its PostHog person, associated events and recordings, even if analytics is opted out or new capture is disabled. Late updates and still-valid session JWTs cannot send new account events through Scout. PostHog can still ingest an event accepted before deletion, so a Durable Object alarm repeats deletion daily, including after a response found no matching person. This reconciliation continues while the integration is configured and incurs background requests. PostHog deletion is asynchronous: an accepted request is **not proof that historical data has been erased**, and operators must check deletion status and replay failed webhook deliveries. Clearing a profile field alone does not remove old `$set` events. The separate Cloudflare prompt archive has no account identifier and is not erased by this sync. These changes do not authenticate or link anonymous CLI telemetry.

## Account sign-in — published, 21 October 2026

Hosted Scout uses Clerk authentication for **Google and GitHub only**, without Clerk Billing, subscriptions or payment collection. Production configuration checks confirmed both providers enabled, no additional required profile fields, and organizations and Billing disabled. The production domain and keys are configured and the serving Worker is deployed. Google/GitHub enablement is a Clerk dashboard setting, not something the source code alone establishes.

The page and index status remain public. **Sign in** opens Clerk's account UI; submitting a task while signed out opens that same flow without invoking matching. A prompt draft is temporarily kept in this tab's `sessionStorage` to survive the OAuth redirect, then removed on return or successful sign-in. Storage-disabled browsers can sign in but may lose their draft during the redirect. Signing out or changing accounts clears the visible prompt/results and cancels the browser's pending request; it does not guarantee cancellation of provider work already accepted by the server.

The Worker verifies Clerk session tokens before catalogue access for both `/scout/api/recommend` and `/scout/mcp`, including MCP discovery. Requests must send `Authorization: Bearer <session token>`; a cookie alone is not enough. Signature, expiry, issuer and authorized-party validation use Clerk's SDK, and pending sessions cannot search. Missing/invalid credentials return HTTP 401; missing server configuration returns 503 rather than enabling anonymous access. Status and `/scout/api/auth` remain public; the latter exposes only the publishable key and frontend API hostname. The secret key never reaches the browser.

For an authenticated development/API check, obtain a current token from `await window.Clerk.session.getToken()` in your own signed-in browser. Treat it as a credential, do not share it, and set it privately as `SCOUT_TOKEN`. Then send:

```sh
curl https://openmerit.ai/scout/api/recommend \
  -H "Authorization: Bearer $SCOUT_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Extract six invoice fields as JSON"}'
```

Use the same header for MCP. These tokens are short-lived; clients must refresh them rather than store one as a permanent API key. This first integration does **not** implement agent OAuth discovery/registration, long-lived API keys, or unattended agent sign-in. Existing clients without a way to supply a current session token now receive HTTP 401 and need an update. Already-issued valid JWTs may remain usable until expiry after session revocation; this is not a per-request online session-status lookup.

The existing edge limiter applies separately to IP addresses and authenticated user IDs: 60 protected requests per minute for each key, including MCP initialization/discovery. It is not a durable monthly usage ledger or a billing cap; the local preview does not emulate Cloudflare's limiter. Clerk handles account/profile and session data and loads its browser SDK/UI from its own frontend API domain. Its optional SDK telemetry is disabled. Raw account IDs are used transiently for rate limiting, not attached to the historical Cloudflare prompt archive. The 22 October analytics release adds pseudonymous account-state storage and the profile sync above; no public saved-search history or billing integration is introduced. PostHog and Clerk have separate retention policies from the historical three-month Cloudflare archive.

Local development now also needs `CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` in the server environment. Configure a Clerk development instance with Google/GitHub sign-in and sign-up; disable other sign-in methods and unnecessary required profile fields. Use the production instance and its own OAuth applications for `openmerit.ai`. Never expose the secret key in client configuration or commit it. The deployed production modal was checked at desktop/mobile sizes, and both buttons reached provider authorization redirects requesting basic identity/email scopes only. Signed-out submissions opened sign-in without a recommendation request and preserved the tab's prompt draft. Hosted API/MCP checks rejected anonymous, invalid-token and cookie-only requests. Tests stopped before provider authentication: complete sign-in/sign-up, callback return and real-user authenticated searches remain unverified. Offline signature tests are not evidence of a complete Google/GitHub login.

## Task sequences — published alpha, 21 October 2026

The [alpha](https://openmerit.ai/scout/alpha/) UI uses a normal Model/Quality/Cost/Time table for one task. For two or three tasks, each task becomes a column in one shared table. Read each row left to right as a sequence of model choices, with quality, reference cost and time beneath each model. Column headings quote short excerpts from the submitted prompt rather than rewriting the work. The five-layer breakdown, role labels, frontier badges and capability tags remain hidden. The table scrolls internally when needed; narrow screens retain the side-by-side order instead of stacking separate task tables.

Rows align each task's independently ranked alternatives; they are **not jointly evaluated workflows**, a global ranking of model combinations, or verified model-to-model dependencies. The top row takes each task's first choice under its existing ranking policy. Five is still a maximum, not a quota: a shorter shortlist leaves an explicit gap, and no model is repeated to complete a sequence. The same model can legitimately appear in different task columns with different evidence and workloads. Expand any model for its task-specific evidence. **Assumptions & limitations** retains quality-screen status, workload, warnings and specialist discovery. Unknown values remain unknown; calibration accuracy is distinct from relative benchmark scores. Costs are USD per 1,000 reference tasks, not exact dataset charges, and are not added into a workflow quote.

Interpreter version 37 requests a short `tasks[].sourceText` excerpt in the existing decomposition call and checks that it occurs verbatim in the prompt. When every excerpt has a unique position, those positions establish task order while keeping restrictions and models attached; otherwise the interpreter's task order is retained. An invalid excerpt becomes `null`, without blocking the shortlist or asking a follow-up question; the UI then uses an unquoted interpreted title (or the original full prompt for a single task). Long headings are visually shortened, with their full text in the hover hint, accessible text and expanded model details. The existing five-layer data and `tasks[].slots[0]` remain; no additional model call, dependency analysis, recommended-model execution or ranking-policy change is introduced. This change is published only to alpha; stable Scout is unchanged.

The deployed HTML, JavaScript and styles matched the checked build; desktop and 390px mobile captures were inspected, including horizontal scrolling and model evidence expansion, with no browser errors or page overflow. ## Newer document evidence — deployed, 22 October 2026

Document and image-reading tasks previously relied on document benchmarks that covered only models from OpenVLM's 17 September 2025 snapshot and four OmniDocBench entries, so receipts and invoices could return GPT-4.1 or GPT-4o. The hourly refresh now imports the [IDP Leaderboard](https://www.idp-leaderboard.org/) component series as three benchmarks. Fourteen of its 26 entries match catalogue models, including GPT-5.4, GPT-5.2, GPT-5 Mini, Gemini 3.1 Pro, Gemini 3 Flash and Claude Opus, Sonnet 4.6 and Haiku 4.5. Benchmark interpretation tags all three series as document and image evidence. Its newest entries still trail the latest releases.

A model with no document-reading result can now qualify for a document task on general image-understanding evidence. Such picks carry `missingEvidence: ["documents"]` and a warning naming them. Quality is still estimated only from accepted evidence; this widens eligibility, not the evidence itself.

The first refresh with this source published catalogue `4efa445856c7eec97819270e48c0e658` (checked 22 October 2026, 13:40 UTC). Replays of invoice and receipt prompts against it returned current models such as GPT-6.1 Sol and Claude Opus 5.5 rather than GPT-4.1 and GPT-4o, but only one or two candidates, both admitted on general image evidence.

In unreleased source, an accepted benchmark counts only for the ability the request-time applicability check confirmed for that task, not for every ability in its hourly interpretation. A spatial-reasoning benchmark accepted as image evidence therefore no longer counts as document evidence or carries document weight.

Also unreleased: models with accepted document evidence are ranked among themselves first, so stronger general image scores elsewhere cannot push them out of the quality band. Image-only fallbacks are ranked separately and fill only the remaining places, after every document-evidenced model. They receive no strongest, best-value or fastest label, and their warning says they are listed after models with document results. With this change alone, replays against the same catalogue returned three or four document-evidenced models for the invoice and receipt prompts, with Claude Opus 5.5 as the only fallback; the margin change below brings both to five document-evidenced models. A cost-priority search lists the cheapest document-evidenced model first.

## Writing, summary and analysis evidence — unreleased

Task interpretation (interpreter 39) distinguishes two narrower abilities: **summarization & synthesis** (a child of writing) and **analysis & recommendations** (a child of reasoning). Searches previously reduced summarizing feedback, prioritizing fixes and writing release notes to the same writing weight, and their only accepted evidence was one creative-writing benchmark covering 20 mostly older models, so all three received one shortlist. The hourly refresh takes core abilities from the released registry; abilities discovered by research are kept.

The hourly refresh adds two sources:

- [Vectara Hallucination Leaderboard](https://github.com/vectara/hallucination-leaderboard) (Apache-2.0): the share of summaries of supplied documents that stay consistent with their source. Models answering fewer than 90% of documents are excluded, because their rate covers only the documents they answered. It measures faithfulness, not summary quality; smaller models often score higher.
- [Arena leaderboard dataset](https://huggingface.co/datasets/lmarena-ai/leaderboard-dataset) (CC BY 4.0): style-controlled human-preference ratings for eight request categories (creative writing; writing, literature and language; business, management and finance; instruction following; hard prompts; multi-turn; longer queries; expert) and the document arena. Ratings become an expected win rate against the median-rated model of the same leaderboard; ratings with confidence intervals wider than 60 points are excluded. Preference is not verified correctness.

A test refresh matched 59 catalogue models to Vectara, about 142 to each Arena text category and 22 to the document arena.

Three changes to quality qualification accompany them:

- **Disagreeing evaluations.** With three or more connected evaluations, one whose scores correlate below 0.3 with the estimate from the others (over at least five shared models) is left out of the common quality estimate. A narrow score range gives such an evaluation very small fitted noise, so it previously dominated the estimate: models with only a Vectara result ranked above every frontier model.
- **Margin and uncertainty.** The practical-equality margin is the larger of two points and 0.15 of the spread of model estimates on the task, so it means a similar share of model differences whichever evaluations a task uses. Each model's standard error also includes how much its own evaluations disagree about it, so one tightly measured evaluation cannot decide a result alone.
- **Agentic evidence.** When a task calls no tools and needs no coding, evaluations interpreted as agentic or tool-calling are not used, unless they are the only accepted evidence; a warning names them. Coding evaluations normally run in agent harnesses and keep them.

Replays of a three-task request (feedback themes, prioritized fixes, release notes) against a test refresh of catalogue `4efa445856c7eec97819270e48c0e658` gave three different shortlists. ## Common quality estimate and labelled tradeoffs — deployed, 22 October 2026

This change replaces the cost-first policy below. Quality screening previously compared a model only with models that had exactly the same set of accepted benchmarks. That split the catalogue into many two- or three-model groups, so the best of a small, weak group passed the screen and cost-first ordering promoted it.

Scout now fits **one latent quality estimate across every connected evaluation** for the task. Each benchmark has its own difficulty offset, score scale and noise, so a near-zero benchmark and a widely spread one contribute on comparable terms. Correlated series in one benchmark family share that family's weight. Each model receives an estimate with a standard error; a benchmark run by only one model links nothing. Applicable calibration observations join as one further evaluation using effective quality. Models with no evidence connected to the main group receive no estimate and remain provisional; they are never compared numerically. The estimate is reported as `comparison.qualityEstimate` and `comparison.qualityStandardError`; `quality` is its relative percentile among the estimated models.

A configuration qualifies when it is not credibly worse than the strongest estimate: within two points plus one combined standard error. Supported Pareto selection over quality, reference cost and reference time follows. A balanced search keeps the strongest, lowest-known-cost and fastest frontier points, labelled in `pick` as `quality`, `value` and `speed`, then orders by estimated quality. An explicit `quality`, `cost` or `latency` priority orders the frontier accordingly. At most two models per provider are selected while other qualifying models remain; the cap never leaves a supported place empty. `ranking.version` is `10`, and `ranking.frontier` reports `version: 4`, the priority, the number of estimated models and benchmarks, and the tolerance.

Reference time previously required measurements bound to the selected endpoint. No published catalogue endpoint had such a binding, so time was unknown for every candidate and dominance never removed one. Endpoint-bound timing still takes precedence and never migrates to another route. Artificial Analysis model-level medians, which are not tied to any endpoint, now apply to each route of that model, marked `speed.scope: "model"`, with a warning that actual endpoint latency may differ.

These remain relative benchmark signals, not task accuracy. An offline replay of the bundled 15 October catalogue, with simulated evidence retrieval, returned frontier coding and reasoning models first instead of the lowest-cost members of small cohorts; it did not execute any recommended model. Ranking added about 6 ms per search locally.

## JSON API

```sh
curl https://openmerit.ai/scout/api/recommend \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Upload an invoice and extract six fields as JSON"}'
```

`POST /scout/api/recommend` requires `prompt`: a non-empty string of at most 4,000 characters. The JSON body is limited to 18,000 bytes. Unknown properties are rejected.

HTTP and MCP additionally accept optional `modelIds`, a unique list of up to 100 legacy OpenRouter catalogue IDs. This preserves the existing-project inventory contract; a model ID alone does not grant a direct-provider endpoint. To select specific routes instead, use `endpointIds`, a unique list of up to 100 IDs returned in `recommendations[].endpoint.id`. Both filters intersect if supplied. This filters eligible candidates before ranking; an empty or unknown-only list returns no models. The response echoes `selection.modelIds` and `selection.endpointIds` (`null` for unscoped). Scoped requests omit specialist discovery because it is outside the declared inventory. No endpoint URL or credential is accepted. The [agent evaluation runner](agent-evaluations.md) uses this for existing-project scope; the hosted API supports it as of 15 October 2026. The npm evaluation commands are available in `openmerit@0.1.7-preview.3` under the `preview` tag, separate from stable `0.1.6`.

Recommendation `id` preserves legacy router IDs; a new protocol receives a distinct catalogue ID. `modelId` is the canonical model identity, while `endpoint.modelId` is the identifier to send to that provider. Clients must use the returned protocol and deployment requirements rather than treating every option as a chat-completions model. Existing npm clients using legacy `modelIds` remain scoped to their router inventory.

The response contains:

- `recommendations`: up to five distinct model IDs with rank, provider, `endpoint` (provider model ID, protocol, configuration, deployment, provenance and limits), reason, quality signal, evidence coverage, input/output pricing, reference timing when available, supported inputs, and source-linked evidence. `reference` gives cost in USD and completion seconds (`null` when unavailable). Benchmark mode includes assumed input/output tokens; measured mode sets those token counts to `null` and supplies `measured` with observed field accuracy, the reliability-capped `effectiveQuality`, cross-task `availability`, valid outputs, sample size, charge coverage, provider routes and evidence provenance. `comparison` gives the number of comparable candidates and average shared-capability coverage. The compatibility `pricing.blendedPerMillion` field retains its old 3:1 calculation but is no longer scored.
- `task`: interpreted capabilities and weights; image-input, structured-output, tool-calling and persistent-memory requirements; `requirements.tools` (`yes`, `no`, `unspecified`); `requirements.memory` (`none`, `session`, `persistent`, `unspecified`); consequential `uncertainty`; `workload.input` and `workload.output` (`short`, `medium`, `long`), `workload.priority` (`balanced`, `quality`, `cost`, `latency`), `kind` (`extract`, `classify`, `dispatch`, `code`, `act`, `remember`, `sql`, `calculate`, `retrieve`, `judge`, `detect`, `segment`, `visual_unspecified`, `other`), `outputContract` (labels, decision, boxes, masks, text, or unspecified), `outputFormat` (`json`, `other`, `none`, or `unspecified`; only specifically established formats can match format-specific calibration), `outputCardinality`, optional `clarification`, and `interpreter: "openai-hybrid"`. `keywords` is retained as an empty compatibility field. A general-purpose fallback means no specific capability was identified, not that the classifier was unavailable.
- `specialists`: a separate discovery object with up to three Hub repositories, metadata-based task fit, declared licenses, pinned model-card revisions, live hosting metadata when supplied, and original reported evaluation records. `mode` is `discovery`; quality, cost and latency are `null`. These candidates are not additional ranked places. Compatible vision deployments may instead enter a task-fit shortlist; they are not counted twice. Unsupported task types can omit this field.
- `specialistRepositories`: bounded Hub catalogue count, separate from the evidence-backed `models` count.
- `calibration`: released task profiles, scopes, sample sizes, measurement dates and expiry status.
- `checkedAt`, `stale`, `degraded`, `sources`: index and source health, feed purpose, limitations and coverage. Each source has its own last successful check. A failed source is marked degraded; any hourly source unchecked for more than two hours makes the index stale. Versioned endpoint contracts disclose their manual review date separately; a scheduled metadata refresh does not renew those price claims.
- `benchmarks`, `benchmarksWithResults`, `models`, `providers`, `availableModels`, `eligibleModels`: indexed series, series with matched results, evidence-backed models, distinct indexed model providers (including alias consolidation), catalogue models, and eligible candidates for this task. `endpoints` counts hosted route listings, including reviewed typed contracts; `independentModels` counts catalogue identities with metadata independent of OpenRouter. Neither number implies credentials or verified account access.
- `wordCloud`: capability vocabulary with benchmark and model coverage counts.
- `ranking`: algorithm version, `mode` (`measured`, `benchmarks`, `task-fit`, or `clarification`), workload and tradeoff weights. A measured `profile` gives the task type, sample size, eligible tested pool, protocol hash, collection and expiry times, and public evidence URL. `benchmarkEligibleModels` reports the separate public-benchmark pool. Rank is the final shortlist order. `ranking.frontier` reports compared configurations, selected distinct models and whether the objective scope is comparable or partial. The compatibility `score` can be `null`; there is no weighted quality/cost/time composite in frontier selection.
- `warnings`, `methodology`, `interpretationMs`, `elapsedMs`: limitations, ranking method, Decisions request time, and measured server ranking time when the runtime provides a sufficiently precise clock (`null` otherwise). Cloudflare freezes its clock during synchronous work, so the hosted page reports measured HTTP round-trip time instead of claiming zero-millisecond computation.

`pricing.url` is the official provider destination, not the source of the quoted rates. It is `null` for a provider without a reviewed destination; the page then omits the link. The same rule applies to MCP responses. `pricing.basis` identifies the price source and calculation assumptions.

`GET /scout/api/status` returns index coverage, source timestamps, freshness, and scheduler state without submitting a prompt. API responses are `no-store`. Errors return JSON with `error`: 400 for invalid input, 413 for an oversized request, 415 for a non-JSON body, 405 for an unsupported method, 404 for an unknown endpoint, 429 when shared admission limits are reached, and 503 if interpretation is unavailable. A failed, malformed, refused, or timed-out Decisions response never silently falls back to keyword ranking. MCP reports these failures as tool errors.

Scout recommends models; it does not process an uploaded invoice, execute a task, install a model, or select a provider account.

## Specialist models and open weights

Some specialist models have useful evaluations outside general LLM leaderboards. Scout reads both legacy model-card `model-index` results and the Hub’s [structured evaluation records](https://huggingface.co/docs/hub/eval-results). It retains the original dataset, task or metric, units, configuration, split, reported date, setup notes and source link when supplied. Scores are not averaged across unrelated datasets. A repository revision pins the metadata collected; it does not establish which checkpoint produced every reported score. Reported dates can also default to a commit date. Scout does not validate verification tokens or independently reproduce these scores.

The hourly discovery sample takes up to 30 repositories sorted by downloads for each of fourteen pipelines: document question answering, token classification, text classification, sentence similarity, text-to-text generation, text generation, image-to-text, image-text-to-text, image classification, zero-shot image classification, object detection, zero-shot object detection, image segmentation and mask generation. The two image-to-text queries remain OCR-filtered. Bounded pinned configs add label vocabularies for up to six repositories in each fixed-label vision pipeline. Private/disabled repositories, adapters and quantization packages are excluded; fine-tunes remain separate. Downloads select coverage only, never quality. This bounded sample can miss capable low-download specialists.

For document, code and retrieval components, **Specialist models** expands beneath the five recommendations when compatible prepared profiles match. For classification, detection and segmentation, compatible native pipelines may enter the five **Candidates to evaluate** instead. Fixed-label pipelines need complete semantic coverage of the requested categories; one overlapping label is insufficient. Zero-shot pipelines accept supplied labels; masks can require points or boxes. Pipeline metadata is not an accuracy guarantee. Up to three components are ordered by metadata completeness and component diversity after compatibility checks. Domain and language requirements come from Decisions, with no prompt keyword dictionary. Tool execution and persistent-memory tasks do not receive unvalidated specialist matches. Entity taggers, OCR and embedding models are components requiring integration, not interchangeable chat APIs. Repeated repository names are de-emphasized for display diversity without merging their identities. See the release status in [semantic specialist matching](#semantic-specialist-matching-hosted-beta-15-october-2026).

Cards show declared licenses, access gates, language, library, parameter count when known, and live hosting routes listed by the Hub. Missing hosting metadata does not prove that no provider exists. Size is not a hardware-fit estimate. Public weights do not establish an open-source license or permission for a particular use; check the pinned model card and actual license. Scout neither downloads weights nor executes repository code, and it does not send task descriptions to Hugging Face.

Missing evaluations mean **unknown**, not poor performance. Task-fit candidates do not receive quality scores through download counts, self-reported results, or general reasoning benchmarks. A performance ranking requires comparable task checks, full workload cost and timing under a recorded deployment configuration. Self-hosted cost depends on hardware and utilization; a zero token price would be misleading. The same quality/cost/speed comparison can then be used without a provider preference. Model-specific exceptions and inferred free inference are not used.

## Ranking

[OpenAI Decisions](https://developers.openai.com/api/docs/guides/decisions), using `gpt-6-luna`, interprets the work, capability requirements, operation, answer space, serialization and tradeoff priority. It distinguishes writing source from executing it, supplied categories from open identification, text-bearing objects from reading their contents, and session state from persistent memory. Typed answers are validated and checked for consistency. Uncertain answers remain disclosed; they cannot authorize narrow calibration evidence. No prompt keyword rules or model-name bonuses enter selection.

A Structured Outputs call first extracts downstream work, explicit model/endpoint restrictions and preferences using the published metadata definitions and canonical vocabulary. Mandatory conditions use alternatives of complete AND groups; exclusions and arbitrary numeric/date bounds are preserved. Relative dates use a supplied current UTC reference. Generic typed comparisons enforce those conditions and intersect optional `modelIds`/`endpointIds` inventories. Missing facts cannot satisfy a restriction, including an exclusion. Unexpressible mandatory restrictions produce no verified matches rather than silently broadening the search. Names mentioned as task data, clients or comparison subjects are not automatic filters. Interpretation is probabilistic and can still misread a prompt.

Image tasks require declared image input and relevant visual evidence in performance ranking. Document reading needs document evidence. JSON/schema tasks need declared `response_format` or `structured_outputs`; required tool execution needs tools support and relevant tool evidence. Persistent memory requires external-memory evidence rather than a large context window. [BFCL memory evaluations](https://gorilla.cs.berkeley.edu/blogs/16_bfcl_v4_memory.html) do not establish built-in memory or performance on the visitor's storage system. Recognized image/video/audio generation and transcription remain outside the supported output index. Ambiguous spatial output produces the existing clarification choices.

Classification and judgment tasks first use applicable benchmark evidence. With no supported benchmark candidates, supplied-label classification and judgments retain the explicitly labelled **task-fit** fallback. Boxes and masks use their compatible task-fit path. Documented operation/output fit, deployment readiness and known reference costs/times determine unmeasured shortlists; quality stays unknown. Open or uncertain identification instead needs name-generating endpoints and relevant evidence; fixed-choice APIs cannot satisfy it. Specialist compatibility uses hourly-prepared public profiles. Unknown compatibility omits a repository with a warning, rather than assuming task accuracy.

For performance ranking, a query embedding retrieves benchmark methodologies, supplemented by their hourly capability memberships. Bounded independent Decisions predicates verify relevance and a deliberately scored required ability before a methodology contributes proxy evidence. Similarity never supplies a quality score. Rejected, unknown and unavailable evidence is withheld. If some checks fail, verified evidence can still be used with an explicit warning; if no applicability can be verified because checks are unavailable, the search returns unavailable rather than reporting a false no-match.

Quality comparisons use shared benchmark results, grouped by correlated family and task capability. Different cohorts are not compared through unrelated percentiles. BFCL uses native function-calling configurations with their original labels; correlated series are one family. Missing scores remain unknown and actual zero remains a score. Model/version matching remains conservative. A relative quality signal is not predicted accuracy or a statistical confidence interval.

Matching calibration observations can supplement quality for their exact operation, format, modality, tools, retention and workload scope. Each admitted model needs at least six calibration cases, and evidence expires after 30 days (seven days before 22 October 2026). An applicable profile past that age stays excluded and the result carries a warning naming the profile and its expiry date, rather than silently using benchmarks only. A match no longer requires five tested models or excludes all untested eligible models. Observations remain tied to their tested router deployment. Repeated calibration request failures still cap effective quality. Calibration episode bills and durations remain source evidence; they are not substituted for only some candidates' reference costs or times. Held-out outcomes and answer keys never enter runtime ranking.

All eligible verified catalogue configurations with relevant evidence enter numerical comparison before model deduplication. A configuration can dominate another only when both have a common quality estimate and known cost and time: it must be at least as good in all three and strictly better in one. Missing objectives and incomparable coverage remain provisional. This cannot establish a global three-objective frontier over every model in the world.

Up to five distinct models represent the supported tradeoffs. Balanced searches keep the strongest, lowest-cost and fastest qualifying frontier points; explicit priorities order the frontier instead. Soft metadata preferences break exact ties. At most two models per provider are selected while alternatives remain. Preferences do not broaden eligibility. There is no weighted quality/cost/time composite. Fewer than five points can remain even when more models are eligible; the API reports eligibility separately from the selected count. Stable IDs resolve exact ties.

Reference input sizes are **1,024 / 4,096 / 32,768 tokens**, and visible output sizes are **128 / 512 / 2,048 tokens**, for short / medium / long. Supplied-label choices use a 16-token output reference. Reference cost is input tokens × advertised input rate + output tokens × advertised output rate. This excludes hidden reasoning, cache effects, image-specific tokenization and other modality charges. Decisions has no output-token charge. Unknown or self-hosted operating cost is not inferred to be zero.

Reference completion time is **time to the first answer token + visible output tokens / throughput**. Endpoint-bound measurements take precedence; otherwise an unbound model-level median applies and is labelled `speed.scope: "model"`. Multiple published configurations retain paired timing before taking a median. Timing bound to one route is not borrowed by another, and early reasoning tokens are not confused with the first answer. Missing timing stays unknown. The page's request duration measures Scout matching, not a recommended model executing the visitor's task.

The shortlist requires evaluation on the visitor's own examples. Public benchmarks, small calibration samples and semantic applicability checks do not prove the optimal membership or order of five models for an arbitrary task. The hosted release uses Clerk accounts for sign-in but adds no public prompt history or additional filter controls. Public methodology embeddings are stored in Vectorize; visitor query vectors are transient. Private prompt-and-evidence analytics are described below.

## Refresh and data handling

The task description is sent to Scout and then to OpenAI for Decisions interpretation, Structured Outputs metadata extraction, a transient query embedding and, when relevant, specialist compatibility/applicability checks. Hourly preparation also sends public repository metadata and benchmark definitions/methodology to Decisions; no user prompts are involved in that refresh. New search analytics use [PostHog](#product-analytics), with prompt text off by default and separate opt-in. Runtime request logging remains disabled. The public index and published calibration aggregates are persisted; prompts are not sent to benchmark sites or recommended-model providers. [OpenAI's API data controls and retention policies](https://developers.openai.com/api/docs/guides/your-data) apply to those provider calls. Scout does not claim zero retention by OpenAI. Hosting infrastructure can have separate request-metadata policies. Clipboard actions occur only when selected. Describe the task rather than pasting actual invoices, credentials or private customer records.

**Historical Cloudflare archive:** before the 22 October consolidation, Scout stored submitted prompts with task categories, ordered shortlists, metrics and supporting public evidence in private Analytics Engine records. New writes have stopped. Historical prompt text is unredacted and may contain personal information or secrets; no separately collected account/visitor identity was attached. These records remain accessible only through authenticated Cloudflare account queries and are neither exported nor erased by the PostHog integration.

Cloudflare [retains Analytics Engine events for three months](https://developers.cloudflare.com/analytics/analytics-engine/limits/) and may sample them; that policy does not apply to PostHog. Earlier records are preserved as collected: version 1 has no prompt, and versions 1–2 have no attached evidence snapshot. Missing historical fields cannot be reconstructed. Neither historical analytics nor current recommendation traces prove task success. Scout has no public history/query endpoint.

Each query starts with batched Decisions questions and can make one verification pass for weak answers, followed by relevant specialist compatibility batches. Task interpretation and specialist comparison share a four-second request budget; catalogue reads and ranking add their own time. Optional verification has at most 750 milliseconds and leaves weak answers uncertain if unavailable. Independent specialist batches run in parallel, with at most 100 questions per call. Transient connection, timeout, rate-limit and server failures can receive one retry within the remaining deadline; valid `Retry-After` delays are honored. Authentication, exhausted-credit and quota failures are not retried. Failed interpretation returns an explicit unavailable response; failed specialist checks omit unverified specialist candidates. No keyword fallback is used. These bounds reduce avoidable waits and failures; they do not guarantee a successful search or a particular latency. In-memory admission allows 32 active requests and 600 starts per minute per Worker isolate; a separate edge limiter allows 60 POST requests per minute per IP. Excess requests fail promptly instead of queuing. These are operational limits, not an account-level billing cap or a throughput guarantee. Credentials remain server-side.

Hourly sources refresh independently; reviewed typed-endpoint contracts retain their manual review dates. Freshness follows each source's prepared policy: public feeds have a two-hour freshness allowance, while incremental research uses the configured seven-day recheck interval. A source does not become stale merely because it follows a longer research interval. Missing or invalid check dates remain overdue, and actual collection or preparation failures remain degraded. A failed download, changed parser format, or unexpected loss of coverage preserves that source's previous evidence and timestamp while healthy sources and prices continue updating. Fresh catalogue removals still remove unavailable models. All fourteen Hub queries and required semantic preparation must succeed for its discovery snapshot to replace the previous one. A complete outage preserves the previous index. Failure and stale status are exposed in both interfaces.

Source content is parsed as data, never executed. Downloads, decompression, and request bodies are size-bounded; source downloads time out. Links are restricted to HTTP(S). The publisher's OpenVLM data URL uses HTTP and lacks transport authentication; the remaining feeds use HTTPS. Scout does not independently authenticate benchmark submissions.

## Hosting and verification

`wrangler.scout.jsonc` defines the Scout Worker, a private R2 catalogue, an hourly Workflow and a SQLite Durable Object coordinating publication. The cron runs at minute 7 UTC. Configure `OPENAI_API_KEY` and `PARALLEL_API_KEY` as Worker secrets. Refreshes build immutable catalogue versions and prepared candidate pools; searches read those pools directly and never pass through the publication coordinator. A running refresh does not block searches against the active catalogue. The first hosted publication must be validated before serving searches; a missing catalogue fails explicitly. The Worker is `openmerit-scout`, the private catalogue bucket is `openmerit-scout-catalogue`, and the Workflow is `openmerit-scout-refresh`. Both API keys are stored as Cloudflare Worker secrets and read from server-side bindings; they are not shipped to the browser. Separate workers.dev and preview URLs are disabled.

Publication records a durable completion receipt after updating the active pointer, pending-research queue and health status. Interrupted publication resumes unfinished work; a lost success reply can be acknowledged again after the lease is released. Replaying a completed publication cannot roll back a newer catalogue or clear a later refresh's lease. Completed research receipts leave the queue only when publication commits; unfinished research retains its original paid job for a later hourly run.

Research rediscovery updates an existing record with the same stable primary key, even when semantic interpretation does not link it to another catalogue record. Different source/version identities remain separate unless the evidence supports a semantic link. Duplicate primary keys fail publication validation; searches continue against the last committed catalogue while a later refresh reuses durable research receipts.
